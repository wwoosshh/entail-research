### Describe the bug

In `process_batch_result_prefill`, the branch that skips finished-in-a-mixed-batch and retracted requests does not advance `logprob_pt`, so every later request in the same batch reads a shifted slice of the flat input-logprob array and is served **another request's prompt logprobs**.

The flat array holds one block per request in batch order regardless of whether that request asked for logprobs. That is why `_apply_prefill_logprobs` advances the cursor outside its `return_logprob` guard ([`batch_result_processor.py:522`](https://github.com/sgl-project/sglang/blob/main/python/sglang/srt/managers/scheduler_components/batch_result_processor.py#L522)):

```python
        if req.return_logprob:
            self.logprob_result_processor.add_logprob_return_values(...)
        logprob_pt += num_input_logprobs
        return logprob_pt
```

The producer agrees: `logits_processor.py` builds `extend_logprob_pruned_lens_cpu` by appending `extend_len - start_len` for every sequence in the batch, using the same formula the consumer uses in `calculate_num_input_logprobs`.

But the skip at [`batch_result_processor.py:307-313`](https://github.com/sgl-project/sglang/blob/main/python/sglang/srt/managers/scheduler_components/batch_result_processor.py#L307-L313) steps over a request without stepping the cursor:

```python
                if (
                    req.finished() and req.inflight_middle_chunks <= 0
                ) or req.is_retracted:
                    # Decode req in a mixed batch, or a retracted req. Keep an
                    # aborted middle chunk in the chunked branch long enough to
                    # drain its accounting without streaming it.
                    continue
```

`logprob_pt` is initialized at line 286 and advanced only at lines 344 and 374, both after this `continue`.

Nothing raises. The assertion in `logprob_result_processor.py` checks the slice **length**, not its offset, and the shift is always backwards, so it never runs off the end. The diagnostic signature is that `input_top_logprobs_val[i]` is indexed per request and stays correct while `input_token_logprobs` is sliced by the cursor and is wrong.

The disaggregated prefill loop already handles exactly this. `disaggregation/prefill.py:703` defines `advance_logprob_pt()` and calls it on each of its skip paths at lines 721, 789 and 797.

Scope: this bites when the skipped request itself requested input logprobs (`logprob_start_len >= 0`). With the default `-1` its block is zero rows and the skip is harmless. Overlap scheduling is on by default and retraction is ordinary under KV pressure, so no unusual flag is required.

### Reproduction

Driving the real `process_batch_result_prefill` on CPU with two prefill requests, the first retracted, `extend_input_len_per_req=[2, 3]` and `extend_logprob_start_len_per_req=[0, 0]`, over a flat array of `[-1.0, -2.0, -30.0, -31.0, -32.0]`:

```
expected (active request's own block)  [None, -30.0, -31.0]
actual                                 [None,  -1.0,  -2.0]   <- the retracted request's values
```

I have a regression test that reproduces this, written against the existing `test_batch_result_processor_hidden_states.py` harness and registered as `register_cpu_ci(est_time=2, suite="base-a-test-cpu")`, so it needs no GPU. It fails on `main` and passes with the cursor advanced. I will open a PR with the fix and that test shortly and link it here.

Related but distinct, so neither covers this path:
- [#34153](https://github.com/sgl-project/sglang/pull/34153) applies the same "consume the slice, skip the attach" idea to the `req.to_finish` path, which routes through the normal branch rather than this skip.
- [#36724](https://github.com/sgl-project/sglang/pull/36724) adds a new `deferred_mm_abort` branch immediately above this `continue` and advances the cursor there, leaving this one unchanged.
- [#32103](https://github.com/sgl-project/sglang/pull/32103) and [#32089](https://github.com/sgl-project/sglang/issues/32089) describe the hidden-states analog and both cite this logprob path as already correct.
