### 🐛 Describe the bug

With the FlexAttention backend, the paged K/V element offset inside the generated
Triton kernel is computed in **int32**. Once `num_gpu_blocks` reaches
`2**31 / (block_size * 2 * num_kv_heads * head_size)` the product wraps negative
and the kernel addresses memory ~4 GiB *below* the K/V base. For a
`num_kv_heads=8, head_size=128, block_size=16` cache that bound is exactly
**65,536 blocks**. Nothing validates `num_gpu_blocks` against it.

The failure has **two modes**, decided only by whether the wrapped address happens
to be mapped: an `illegal memory access`, or **no error at all** — the kernel
silently reads the neighbouring allocation and returns wrong attention output.
Because vLLM allocates several ~4 GiB KV pools at descending addresses, the
wrapped address usually lands inside *another KV pool*, so the silent mode is the
common one.

### Where the int32 comes from

`vllm/v1/attention/backends/flex_attention.py` builds `kv_indices` as int32
(still true on `main` as of 2026-07-30):

```python
kv_indices = unique_static_unsorted((used_pages_padded.long()), M=self.num_blocks).to(torch.int32)
kv_indices = copy_to_persistent(self.persistent_kv_indices, kv_indices)

self.persistent_kv_indices = torch.empty(
    self.max_num_query_groups, self.max_num_kv_indices,
    dtype=torch.int32, device=self.device)
```

so every downstream term stays in that dtype (`kv_start = kv_indices * block_size`,
`ptr = K + offs_n * stride_kn`). The generated kernel does define
`INDEX_DTYPE = tl.int64`, but only the **output store** indices go through it; the
K/V gather offsets do not.

What makes the offset exceed the K tensor's own `numel` is that **K and V share one
buffer**, so the K view's maximum linear offset spans the *whole* buffer while its
`numel` is only half of it. Inductor appears to pick the index dtype from `numel`
(~1.12e9 here, which fits int32) rather than from the stride-derived maximum offset
(~2.24e9, which does not).

⚠️ **The packing axis differs between releases — this needs updating before
submitting.** Our environment (`0.23.1rc1.dev813+g344609ab1`) packs on a dedicated
dim and splits with `unbind`:

```python
# flex_attention.py:133 (dev813, what we measured)
return (num_blocks, 2, block_size, num_kv_heads, head_size)
# flex_attention.py:1245 / :1350
key_cache, value_cache = kv_cache.unbind(1)
```

`main` (2026-07-30) packs into the content dim instead:

```python
# K and V are packed into the content dim: logical (B, H, N, 2*hs).
return (num_blocks, num_kv_heads, block_size, 2 * head_size)
...
kv_cache = kv_cache.transpose(1, 2)
key_cache, value_cache = kv_cache.split(hs, dim=-1)
```

The bound is **unchanged** by this, because in both layouts the buffer holds
`num_blocks * block_size * (2 * num_kv_heads * head_size)` elements and the K view's
maximum offset reaches the far end of it:

```
max_safe_num_gpu_blocks = 2**31 // (block_size * 2 * num_kv_heads * head_size)
                        = 2**31 // (16 * 2 * 8 * 128) = 65,536
```

but the *per-token* stride differs, so **the `main` derivation above is analytical —
we measured the `unbind` layout, not the packed one.** Re-run snippet (b) against
`main`'s layout before filing.

Bisecting one property at a time on the layout we did measure, the shared buffer is
the only necessary condition: replacing the two strided views with separate
contiguous K/V tensors halves the stride and doubles the bound. `kv_indices`
contiguity, Q layout, `enable_gqa`, `Q_LEN` alignment and `KV_LEN` magnitude are all
irrelevant.

Also note `kv_cache_utils.py` now has a `_use_packed_kv_cache_config` /
`_get_packed_kv_cache_layout` path returning a `block_stride`; whether that changes
the effective stride for this backend is **not checked**.

### Who is exposed

`num_blocks = available_memory // (group_size * page_size)` where
`group_size = max(len(g.layer_names) for g in kv_cache_groups)` — the number of
memory pools the hybrid allocator creates. **Exposure grows as `group_size`
shrinks**, so models whose layers split into many KV cache groups are the most
exposed; a uniform single-group model needs proportionally more memory to reach
the bound.

Being upfront about our own trigger: we reached `num_gpu_blocks = 70,315` with an
**out-of-tree** backend whose per-layer window config split 36 layers into 4
groups (`group_size = 9`, 37.56 GiB of KV cache). The same 36 layers as a single
group give only ~17,579 blocks. So this is not straightforward to reproduce with a
stock uniform model on one 80 GB card — hence snippet (b), which exercises the
kernel-level mechanism directly and needs neither vLLM nor weights.

In memory terms the bound is `4 GiB * group_size` of KV cache per pool group
(bf16, this layout).

Two-mode summary:

| condition | result |
| --- | --- |
| block id < bound | correct |
| block id ≥ bound, wrapped address unmapped | `CUDA error: an illegal memory access was encountered` |
| block id ≥ bound, wrapped address **mapped** | **no error — silently reads the neighbouring allocation, wrong output** |

Consistent with a latent bound rather than a workload issue: everything that
appeared to "fix" it — lowering `gpu_memory_utilization`, capping `max_num_seqs`,
enabling eviction, `PYTORCH_NO_CUDA_MEMORY_CACHING=1` — merely keeps the allocator
from handing out block ids at the top of the pool.

### Upstream status

The int32 offset arithmetic itself lives in PyTorch's generated FlexAttention
kernel and **has since been fixed**:
[pytorch#190857](https://github.com/pytorch/pytorch/issues/190857) (closed) and
[PR #185264](https://github.com/pytorch/pytorch/pull/185264), which adds an
`INDEX_DTYPE` parameter to `load_checked_2d` and casts the offsets before they are
multiplied by strides, at every call site in the forward, backward and common
templates.

So on a torch that carries #185264 this should no longer be reachable, even with
int32 `kv_indices`. It remains reachable on releases without it — ours
(`2.11.0+cu128`) has `INDEX_DTYPE` appearing zero times in
`torch/_inductor/kernel/flex/templates/utilities.py.jinja`.

### Suggested mitigations on the vLLM side

1. **Validate at start-up** (cheap, no perf impact): warn or clamp when
   `num_gpu_blocks` exceeds
   `2**31 // (block_size * kv_packing * num_kv_heads * head_size)` and the running
   torch lacks the fix. We do this out-of-tree by wrapping
   `kv_cache_utils.may_override_num_blocks`; it cost 4.1% of pool capacity
   (70,315 → 65,536 blocks, 243,350 → 233,263 tokens) with no measurable
   throughput change, and it removed both failure modes.
2. Or declare a **minimum torch version** for the FlexAttention backend.
3. Optionally, a **non-interleaved** K/V layout for this backend — halving the row
   stride doubles the bound regardless of the torch version.

FWIW the `persistent_rswa_kv_indices` comment in the same file already documents
an adjacent hazard ("... producing an out-of-bounds K/V pointer and a CUDA illegal
memory access") and fixes it for the R-SWA path only; this report is the
non-R-SWA path with a different mechanism.
