## Summary

Two Triton GEMMs used by quantized MoE serving get the K tile wrong, and in both cases a sibling code path already does it correctly.

1. **`fused_moe_kernel_gptq_awq` reads the packed weights out of bounds.** The kernel builds `k_mask` whenever `K` is not a multiple of `BLOCK_SIZE_K` and applies it to the scale load and to *both* zero-point loads, but the weight load itself is unmasked, so the last K iteration reads past the end of the weight tensor. The sibling `fused_moe_kernel` masks the identical load. The numbers that come back are multiplied by a scale that *is* masked to zero, so the arithmetic result is unaffected — this is a memory-safety bug, not a numerical one.

2. **`w8a8_triton_block_scaled_mm` can pick one scale for a tile that spans several quantization groups.** `_w8a8_triton_block_scaled_mm` reads a single scale pair per K tile, indexed by `(k * BLOCK_SIZE_K) // group_k`, which is correct only when `BLOCK_SIZE_K` divides `group_k`. Nothing enforces it, and the comment above the default config states the requirement inverted — "BLOCK_SIZE_K must be divisible by block_size[1]" — which is exactly the configuration that breaks. The fused-MoE launcher clamps this (`BLOCK_SIZE_K = min(BLOCK_SIZE_K, min(block_shape[0], block_shape[1]))`); this one does not.

Neither is caught today because the shipped defaults stay inside the safe range: `w8a8_triton_block_scaled_mm`'s default config sets `BLOCK_SIZE_K = block_k`, and `test_fused_moe_wn16` only uses `k` values of 128 and 1024, which are multiples of every `BLOCK_SIZE_K` the untuned path picks. The exposure in both cases is the tuning-config lookup, which reads `BLOCK_SIZE_K` straight out of a JSON file in `configs/` — and the wna16 files there already carry `BLOCK_SIZE_K` values of 128 (168 entries) and 256 (118 entries).

The GPTQ/AWQ MoE kernel was added in #12185 and the block-FP8 GEMM in #11523.

## Reproduction

Both scripts drive the library's own launchers — `dispatch_fused_moe_kernel` and `w8a8_triton_block_scaled_mm` compute the grid and every kernel argument — against this repo at HEAD, installed with `VLLM_USE_PRECOMPILED=1 pip install -e .`.

**1. Out-of-bounds weight read.** An int4 `w4a16` MoE matmul through `invoke_fused_moe_kernel`, with `K = 96` and `BLOCK_SIZE_K = 64`. The packed weight tensor is `[E, N, K // 2]` uint8, so each row holds 48 bytes while the loop covers 64. The weight tensor is allocated last so that the overrun lands in unallocated memory rather than in a neighbouring tensor, which is what makes it visible to `compute-sanitizer`.

```
$ PYTORCH_NO_CUDA_MEMORY_CACHING=1 compute-sanitizer --tool memcheck python repro_gptq_awq.py

  K= 128 BLOCK_SIZE_K= 64: qweight holds 64 bytes per row, the loop covers 64  -> exact fit
      ERROR SUMMARY: 0 errors
  K= 128 BLOCK_SIZE_K= 32: qweight holds 64 bytes per row, the loop covers 64  -> exact fit
      ERROR SUMMARY: 0 errors
  K=  96 BLOCK_SIZE_K= 64: qweight holds 48 bytes per row, the loop covers 64  -> 16 bytes past the end
      reported at vllm/model_executor/layers/fused_moe/fused_moe.py:236
      ERROR SUMMARY: 8 errors
  K=  48 BLOCK_SIZE_K= 32: qweight holds 24 bytes per row, the loop covers 32  -> 8 bytes past the end
      reported at vllm/model_executor/layers/fused_moe/fused_moe.py:236
      ERROR SUMMARY: 8 errors
```

The reported line is the unmasked `b = tl.load(b_ptrs)`, and each access lands past the end of `qweight`:

```
========= Invalid __global__ read of size 1 bytes
=========     at fused_moe_kernel_gptq_awq+0xc40 in fused_moe.py:236
=========     by thread (127,0,0) in block (7,0,0)
=========     Access to 0x7f0eb2405e0f is out of bounds
=========     and is 16 bytes after the nearest allocation at 0x7f0eb2402e00 of size 12288 bytes
```

Under memcheck the launch then fails with `CUDA error: unspecified launch failure`; without the sanitizer the read silently returns whatever is mapped. (The error count is not a property of the defect — the driver kills the context after a variable number of reported accesses — so the fault site is the signal, not the number.)

**2. Wrong scales for an oversized K tile.** `w8a8_triton_block_scaled_mm` against a dequantize-and-matmul reference, `block_shape = [128, 128]`, with the config lookup standing in for a tuned `configs/*.json`:

```
controls: BLOCK_SIZE_K divides group_k
  BLOCK_SIZE_K=  64  group_k=128  (requested tile inside one group)   max relative error 2.226e-07
  BLOCK_SIZE_K= 128  group_k=128  (requested tile inside one group)   max relative error 2.082e-07

bug: BLOCK_SIZE_K a multiple of group_k, which is what the comment asks for
  BLOCK_SIZE_K= 256  group_k=128  (requested tile spans 2 groups)   max relative error 2.284e-01
  BLOCK_SIZE_K= 512  group_k=128  (requested tile spans 4 groups)   max relative error 2.633e-01
```
