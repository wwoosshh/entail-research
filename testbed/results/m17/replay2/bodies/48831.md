### 🐛 Describe the bug

## Summary

When the `/score` or `/rerank` endpoint is called with long query+document pairs (>8K total tokens, but well within `max_model_len`), the returned score is abnormally low (close to 0). The same inputs processed via offline `LLM.score()` produce correct scores (close to 1 for matching pairs).

## Reproduction

1. Serve `Qwen3-Reranker-0.6B` with the command above.
2. Send a `/score` request where query + document total exceeds ~8K tokens.
3. Compare the response score with the same inputs run via `LLM.score()` (offline).

## Diagnostic Findings

- `input_ids` are identical between online and offline modes — preprocessing is correct.
- `use_activation` is `True` in both modes — sigmoid is applied.
- `--enforce-eager` does **not** fix the issue.
- Placing `torch.cuda.synchronize()` in `ClassifierPoolerHead.forward()` fixes the scores — confirming it's an async race condition, not a CUDA Graph bug.

## Root Cause

In `utils.py`, `CpuGpuBuffer.copy_to_gpu()` performs an asynchronous copy with `non_blocking=True`:

```python
# vllm/v1/utils.py line 140-142
def copy_to_gpu(self, n=None):
    if n is None:
        return self.gpu.copy_(self.cpu, non_blocking=True)  # ← async!
    return self.gpu[:n].copy_(self.cpu[:n], non_blocking=True)
```

This is called for `query_start_loc` in `vllm/v1/worker/gpu_model_runner.py:2049`:

```python
self.query_start_loc.copy_to_gpu()
query_start_loc = self.query_start_loc.gpu[: num_reqs + 1]
```

`query_start_loc` is later used by `build_pooling_cursor()` to compute `last_token_indices_gpu`, which indexes into the model's hidden states to extract the last token's embedding:

```
query_start_loc → cumsum → last_token_indices_gpu → hidden_states[...] → h_last
```

When the async CPU→GPU copy hasn't completed by the time the pooler reads `query_start_loc`, `last_token_indices_gpu` points to wrong token positions, producing an incorrect `h_last` → incorrect `W_score · h_last` → sigmoid → near-zero score.

This race is more likely to trigger on long sequences because:

- Long sequence GPU kernels take longer to execute, widening the async gap window.
- Shorter sequences complete GPU work before the async copy race manifests.

## Fix

**Option A (minimal, targeted):** Remove `non_blocking=True` from `CpuGpuBuffer.copy_to_gpu()`:

```python
def copy_to_gpu(self, n=None):
    if n is None:
        return self.gpu.copy_(self.cpu)   # synchronous
    return self.gpu[:n].copy_(self.cpu[:n])
```

**Option B (lighter):** Add `torch.cuda.synchronize()` in `build_pooling_cursor()` after `cumsum.to(device, non_blocking=True)` to ensure completion before `last_token_indices_gpu` is consumed.

## Impact

All V1 engine pooling models using the `classify` task (cross-encoder / sequence classification) are potentially affected when processing long sequences. Bi-encoder and late-interaction models may also be affected if they rely on `query_start_loc` for indexing.
