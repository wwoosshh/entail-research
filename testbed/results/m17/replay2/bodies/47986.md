### 🐛 Describe the bug

### Current environment

Testing against commit `2afa3f7e9` on `main`, CPU-only (bug is not GPU-dependent — reproducible via direct unit-level engine calls, no model inference required).

### 🐛 Describe the bug

`DeepSeekV4Parser._convert_args` (and the identical copy in `DeepSeekV32Parser._convert_args`) in `vllm/parser/deepseek_v4.py` / `vllm/parser/deepseek_v32.py` looks up which tool slot a given raw argument string belongs to using **exact string equality** across all active tool-call slots:

```python
func_name = next((s.name for s in self._tool_slots if s.args == raw_args), None)
```

When two parallel tool calls happen to have **identical raw argument text at the same point during parsing** (e.g. both wrap the same value in an `{"arguments": {...}}` envelope), this lookup returns the **first matching slot**, not necessarily the slot actually being converted. The returned `func_name` is then used to decide whether to unwrap the args against that tool's schema (`_unwrap_wrapper_args`). This means one tool call can be unwrapped using a **different tool's schema and name**, producing silently incorrect arguments.

This affects **both the streaming and non-streaming paths**, since `_convert_args` backs both `_compute_arg_delta` (streaming) and the final extraction call (non-streaming) — this is not a parity issue, it's a correctness bug in the unwrap logic itself.

### Minimal repro

```python
from unittest.mock import MagicMock
from vllm.parser.deepseek_v4 import DeepSeekV4Parser
from vllm.entrypoints.openai.chat_completion.protocol import ChatCompletionToolsParam, FunctionDefinition

def make_tool(name, properties):
    return ChatCompletionToolsParam(
        type="function",
        function=FunctionDefinition(name=name, parameters={"type": "object", "properties": properties}),
    )

# tool_a's schema permits unwrapping "city"; tool_b's schema does not (only has "tz")
tools = [
    make_tool("tool_a", {"city": {"type": "string"}}),
    make_tool("tool_b", {"tz": {"type": "string"}}),
]

tok = MagicMock()
tok.get_vocab.return_value = {}
tok.decode.side_effect = lambda ids: f"tok{ids[0]}"

engine = DeepSeekV4Parser(tok, tools=tools)
req = MagicMock()
req.tools = tools
req.tool_choice = "auto"

# Both invokes wrap identical raw args at the same point in their streams
text = (
    '<｜DSML｜tool_calls>'
    '<｜DSML｜invoke name="tool_a">'
    '<｜DSML｜parameter name="arguments" string="false">{"city": "Tokyo"}</｜DSML｜parameter>'
    '</｜DSML｜invoke>'
    '<｜DSML｜invoke name="tool_b">'
    '<｜DSML｜parameter name="arguments" string="false">{"city": "Tokyo"}</｜DSML｜parameter>'
    '</｜DSML｜invoke>'
    '</｜DSML｜tool_calls>'
)

result = engine.extract_tool_calls(text, req)
for tc in result.tool_calls:
    print(f"{tc.function.name} -> {tc.function.arguments}")
```

**Actual output:**
```
tool_a -> {"city": "Tokyo"}
tool_b -> {"city": "Tokyo"}
```

**Expected output:**
```
tool_a -> {"city": "Tokyo"}
tool_b -> {"arguments": {"city": "Tokyo"}}
```

`tool_b`'s schema only declares `tz`, not `city` — its raw args should remain wrapped since `city` isn't a valid unwrap target for its schema. Instead it inherited `tool_a`'s unwrap decision because the two slots' raw argument text was identical at lookup time.

### Impact

This is a silent-data-correctness bug rather than a crash or malformed output — the resulting JSON is well-formed, but may be validated against and delivered under the wrong tool's schema in a parallel tool-call scenario where argument text happens to collide (plausible with repeated/default values like dates, session IDs, or common parameter names across tools).

### Suggested fix direction

The slot lookup should use positional/identity tracking (e.g. matching by the actual slot index being converted, which the calling code already has via `idx` in `_compute_arg_delta`/`_flush_arg_converter`) rather than searching all slots by content equality. Happy to submit a PR — `_convert_args` would need `idx` threaded through from its callers instead of re-deriving `func_name` via a slot scan.

Related to #47977 , different root cause, same general area (streaming parser engine argument handling).
