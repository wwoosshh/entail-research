### 🐛 Describe the bug

## Summary

For a `Mistral3ForConditionalGeneration` checkpoint (Ministral-3 family) in
HF format, vLLM produces deterministic gibberish (grammatically-plausible,
real-vocabulary, multi-language tokens with no coherent meaning) regardless
of prompt, while plain `transformers.generate()` on the identical checkpoint
is fully coherent. No error or warning is raised at load time.

Root cause: `transformers`' own `Mistral3Config.__init__` (the top-level
composite-wrapper config class) hardcodes `tie_word_embeddings: bool = True`
as its own signature default and never reads/syncs it from `text_config` --
while `Ministral3Config` (the nested `text_config` class actually used for
the language model) independently defaults to `tie_word_embeddings=False`.
These are two different classes with two different hardcoded defaults, so
any checkpoint whose `config.json` doesn't explicitly pin both fields (e.g.
the pristine base model itself) loads with a latent conflict between them --
before any merge/export/fine-tuning is involved. `transformers`' own
weight-tying logic uses `text_config` (confirmed: `transformers.generate()`
is coherent, and the checkpoint's `lm_head.weight`/`embed_tokens.weight` are
verifiably distinct tensors, see below), so the top-level field is
functionally vestigial there and the mismatch is invisible to `transformers`
itself. vLLM appears to resolve tying from the top-level field instead,
silently discards the checkpoint's real, correctly-trained `lm_head.weight`,
and computes output logits through `embed_tokens.weight` instead --
explaining the exact symptom (valid vocabulary, incoherent output) with no
load-time error, since a redundant `lm_head` tensor under an assumed-tied
model is normally dropped silently by vLLM's weight loader rather than
flagged.

## Environment

- vLLM 0.25.1
- Checkpoint: HF-format LoRA-merge of `mistralai/Ministral-3-8B-Base-2512`
  (`architectures: ["Mistral3ForConditionalGeneration"]`, `model_type:
  "mistral3"`, nested `text_config.model_type: "ministral3"`)
- Reproduced under both vLLM's native `Mistral3ForConditionalGeneration`
  implementation and `model_impl="transformers"` (the generic
  Transformers-modeling-backend fallback) -- **identical** gibberish output
  under both, including in `enforce_eager=True` mode (CUDA graphs ruled
  out). This points to the bug being in something vLLM's engine does
  identically across both model-implementation backends (weight-tying
  resolution), not in either backend's own forward-pass/kernel code.

## Relevant config.json fields

```json
{
  "architectures": ["Mistral3ForConditionalGeneration"],
  "model_type": "mistral3",
  "tie_word_embeddings": true,
  "text_config": {
    "model_type": "ministral3",
    "tie_word_embeddings": false,
    ...
  },
  ...
}
```

The base model (`mistralai/Ministral-3-8B-Base-2512`) itself has no
`tie_word_embeddings` field at either level in its raw `config.json` -- the
conflict above only becomes visible once the config is loaded into Python
objects (`Mistral3Config`/`Ministral3Config`'s differing defaults fill it
in) and then re-serialized, e.g. by a LoRA-merge/export step's
`save_pretrained()` call (LLaMA-Factory's `llamafactory-cli export` in our
case). That serialization step isn't introducing the conflict -- it's
faithfully writing out a conflict that already exists in `transformers`'
own class defaults for this model family, latent in the base model from the
moment its config is parsed. So this isn't specific to merged/fine-tuned
checkpoints: any HF-format Mistral3/Ministral3-family checkpoint without
both fields explicitly pinned could hit this in vLLM.

## Verified NOT the cause (ruled out before landing on this)

- **Corrupted/incomplete merge weights**: `transformers.generate()` on the
  identical checkpoint is coherent.
- **Weights silently left at random init / silently-skipped checkpoint
  tensors**: checked `vllm/model_executor/model_loader/default_loader.py`'s
  `DefaultModelLoader` and `AutoWeightsLoader` -- both raise `ValueError` if
  any model parameter never receives a checkpoint tensor, or if an
  unexpected/unmapped checkpoint tensor doesn't match a model parameter
  (unless explicitly allowlisted, e.g. `.bias`). Loading succeeds without
  error here, so this isn't a plain missing/unmapped-weight situation.
- **CUDA graph / kernel-fusion corruption**: reproduced identically with
  `enforce_eager=True`.
- **RoPE (YaRN) `rope_parameters` handling**: this checkpoint's
  `text_config.rope_parameters` uses `rope_type: "yarn"` with `mscale`/
  `mscale_all_dim` fields vLLM's YaRN implementation doesn't extract
  (confirmed via `vllm/model_executor/layers/rotary_embedding/__init__.py`'s
  `get_rope()` allowlist) -- flagged and tested as a hypothesis, but
  injecting a corrective `attn_factor` (computed to cancel the resulting
  ~1.277x default mscale back to the reference implementation's 1.0)
  produced byte-for-byte near-identical gibberish, ruling this out as the
  (or at least the primary) cause.
- **vLLM's own `Mistral3ForConditionalGeneration` implementation
  specifically**: `model_impl="transformers"` (bypassing vLLM's
  hand-written `mistral3.py` entirely) reproduces the identical output.

## Confirmed: lm_head and embed_tokens are genuinely untied in this checkpoint

```python
from safetensors import safe_open
import torch

with safe_open("model-00001-of-00004.safetensors", framework="pt") as f:
    lm_head = f.get_tensor("language_model.lm_head.weight")
    embed = f.get_tensor("language_model.model.embed_tokens.weight")

torch.equal(lm_head, embed)  # False
(lm_head.float() - embed.float()).abs().max().item()  # 0.32110595703125
```

## Fix that resolves it (tested)

Patching only the top-level `tie_word_embeddings` field to match the nested
`text_config.tie_word_embeddings` (leaving everything else, including the
actual weights, untouched) fully resolves the issue. Validated end-to-end:
ran the same checkpoint through a full production evaluation harness (37
real judge-classification datasets, full sample counts, not a toy subset)
both before and after the patch -- before: uniform incoherent gibberish
regardless of dataset; after: real, varied, discriminating metrics (accuracy
0.65-1.0, F1 0.46-1.0, sensible TP/TN/FP/FN splits) closely matching a
known-good `transformers.generate()`-based baseline run on the same
checkpoint/datasets.

## Suggested root-cause fix

For composite VLM wrapper classes like `Mistral3ForConditionalGeneration`,
`vllm/model_executor/models/mistral3.py`'s `__init__` already passes
`hf_config=config.text_config` (not the top-level composite config) when
constructing the inner language model via `init_vllm_registered_model(...)`
-- i.e. vLLM already treats `text_config` as authoritative for that
submodel's architecture/layer construction. Whatever resolves the
weight-tying decision for that inner language model should be consistent
with this and also read `tie_word_embeddings` from that same `text_config`,
rather than (apparently) falling back to the top-level
`vllm_config.model_config.hf_config.tie_word_embeddings`. We haven't
pinpointed the exact line responsible -- happy to help narrow it down
further if useful, but wanted to report given how solid the repro/diagnosis
is and how easy the corruption is to miss (no error, no warning, output is
merely wrong rather than absent).

## Practical workaround for anyone else hitting this

Before loading via vLLM, patch the checkpoint's `config.json`:

```python
import json
with open("config.json") as f:
    cfg = json.load(f)
cfg["tie_word_embeddings"] = cfg["text_config"]["tie_word_embeddings"]
with open("config.json", "w") as f:
    json.dump(cfg, f, indent=2)
```
