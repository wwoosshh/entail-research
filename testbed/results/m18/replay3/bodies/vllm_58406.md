### 🐛 Describe the bug

## Summary

While investigating the two Qwen3-VL failures reported in #56363 and discussing the fix in #56372, we found that they expose a broader issue in the common `mm_processor_kwargs` handling:

- vLLM accepts processor kwargs from both engine configuration and per-request overrides
- and supports both legacy flat kwargs and Hugging Face modality-scoped kwargs such as `images_kwargs` and `videos_kwargs`.
  - For example, a video setting like `fps` can be provided either as a flat kwarg (`{"fps": 2}`) or under `videos_kwargs` (`{"videos_kwargs": {"fps": 2}}`).

However, there is currently no single merge/resolution contract covering both dimensions. Depending on how the same effective settings are split across source (engine vs request) and scope (flat vs modality-scoped), values can be dropped, precedence can change, or flat/scoped representations can become conflicting again later in the processing path.

## Why the current merge/resolution is insufficient

The current common path first performs a shallow top-level merge of engine and request kwargs, then overlays a modality scope for vLLM-side reads. A single example shows the problem:

```python
from vllm.config.multimodal import MultiModalConfig
from vllm.multimodal.processing.context import overlay_modality_mm_kwargs

config = MultiModalConfig(
    mm_processor_kwargs={
        "size": {
            "shortest_edge": 100,
            "longest_edge": 1000,
        },
        "videos_kwargs": {
            "fps": 2,
            "size": {
                "longest_edge": 1200,
            },
        },
    },
    mm_device_do_normalize=False,
)

request = {
    "size": {
        "longest_edge": 1800,
    },
    "videos_kwargs": {
        "size": {
            "shortest_edge": 200,
        },
    },
}

merged = config.merge_mm_processor_kwargs(request)
video = overlay_modality_mm_kwargs(merged, "video")

print(merged)
print({"fps": video.get("fps"), "size": video.get("size")})
```

The top-level merge replaces both nested mappings wholesale, and the subsequent video overlay replaces the remaining flat `size` mapping again.

The effective video result is therefore:

```text
{'fps': None, 'size': {'shortest_edge': 200}}
```

but the expected effective values are:

```text
{'fps': 2, 'size': {'shortest_edge': 200, 'longest_edge': 1800}}
```

This result follows from the two dimensions of precedence that need to be considered together:

```text
engine flat
< engine scoped
< request flat
< request scoped
```

For example, request flat `longest_edge=1800` must override engine-scoped `longest_edge=1200`, while request-scoped `shortest_edge=200` must override engine flat `shortest_edge=100`. `fps=2` should remain because the request does not override it.

So fixing only the shallow nested merge is not enough: the common handling also needs to preserve the relationship between source precedence and modality specificity.

<details>
<summary>Why flat kwargs cannot simply be assigned to one modality</summary>

Legacy flat kwargs can apply to more than one modality. For example, if both the image and video processors support `size`:

```python
{
    "size": X,
    "videos_kwargs": {
        "size": Y,
    },
}
```

the effective settings are conceptually:

```python
image: size = X
video: size = Y
```

The flat value remains the default for every modality that supports it, while the scoped value overrides it only for video. A common resolver therefore needs to preserve shared flat semantics without leaking scoped overrides into sibling modalities.

</details>

The resolved representation also needs to remain stable if it passes through another merge path. If an engine-level flat `size=X` has already been resolved to `videos_kwargs.size=Y`, a later merge must not reconstruct both representations.

That is the runtime manifestation seen in #56363, where Transformers eventually receives `size` both flat and under `videos_kwargs` and rejects it:

```text
ValueError: Keyword argument size was passed two times:
in a dictionary for videos_kwargs and as a **kwarg.
```

Transformers is correctly rejecting an ambiguous input here; the issue is that vLLM can construct or reconstruct that representation before the HF processor call. The full runtime reproduction and traceback are already available in #56363.

## Model-specific semantic aliases

There is one additional requirement that the common layer cannot infer by itself: some models expose different kwargs for the same effective setting.

For models based on Qwen2-VL/Qwen3-VL:

```text
size.shortest_edge ↔ min_pixels
size.longest_edge  ↔ max_pixels
```

<details>
<summary>Example: Qwen aliases across engine and request</summary>

```python
engine = {
    "images_kwargs": {
        "min_pixels": 64,
    }
}

request = {
    "images_kwargs": {
        "size": {
            "shortest_edge": 128,
        },
    }
}
```

A purely structural merge sees `min_pixels` and `size.shortest_edge` as unrelated keys. Qwen semantics, however, treat them as equivalent controls, so the request-level `128` must retain precedence over the engine-level `64`. **With the current merge, that precedence is not preserved because the two aliases are handled as independent keys.**

</details>

vLLM can define the precedence between engine and request values across flat and modality-scoped representations, but model-specific code needs to identify semantic aliases before that precedence can be applied correctly.

## Expected behavior

`mm_processor_kwargs` should have stable semantics across engine configuration, request overrides, vLLM-side reads, processor construction, and the final HF processor call:

* when engine and request both provide nested kwargs, request values override only the nested keys they specify, while the remaining engine-provided keys are kept;
* request values override engine values even when the two use different flat/scoped representations;
* within the same source (engine or request), modality-scoped values take precedence over flat values for that modality;
* scoped values affect only their modality, while flat kwargs continue to apply to every modality that supports them;
* once a value has been resolved into a modality scope, later processing must not reintroduce a lower-priority flat copy of the same setting;
* model-specific aliases are resolved to the same effective setting before vLLM applies engine/request precedence.
