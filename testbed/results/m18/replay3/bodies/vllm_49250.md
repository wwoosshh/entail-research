### 🐛 Describe the bug

### Description

With `kv_load_failure_policy="recompute"`, when a KV connector promises externally cached prefix tokens and the load is then rejected, the request is recomputed but its output is wrong. It does not match a clean run with no connector, even though the rejected load moved no data. Recovery reports success (`Recovered from KV load failure: 1 request(s) rescheduled`), but the decoded result is garbage under synchronous scheduling and an offset continuation under asynchronous scheduling.

This also breaks the invariant that the `examples/disaggregated/kv_load_failure_recovery_offline` example checks, which is a `cmp -s` of the recovered output against the baseline. That example runs Llama-3.2-1B, which uses the V2 runner, but it is an example script that is not run in CI, so the regression went unnoticed.

### Setup

- vLLM `0.25.1`. The affected code is byte-identical on `main`.
- The V2 GPU model runner, which is the default for any non-MoE generative model (Qwen3, Llama-3.2, and similar). The startup log shows `Using V2 Model Runner`.
- Single GPU, TP=1, FlashAttention-2, `--enforce-eager`, `--no-enable-prefix-caching`.
- A custom `KVConnectorBase_V1` (`kv_role="kv_both"`) doing a synchronous load (`get_num_new_matched_tokens` returns `load_async=False`), with `kv_load_failure_policy="recompute"`.

The two scheduling modes fail differently. They share a root cause, and async scheduling adds a second problem on top of it:

| Run | Scheduling | Output (greedy, prompt "...The capital of Italy is") |
|-----|-----------|-----------------------------------------------------|
| baseline (no connector) | either | `[' Rome', ',', ' and', ' the', ' capital', ' of', ' Spain', ' is']` |
| reject, then recompute | sync (`--no-async-scheduling`) | `' tntn tntn tnt'` (garbage) |
| reject, then recompute | async (default) | `' country in Europe. It is known for'` (wrong) |

The exact corruption depends on the residual KV. If the promised-but-never-filled prefix block happens to hold usable stale KV, the output can read like a coherent one-token shift; otherwise it is garbage.

## Minimal reproduction

A connector that promises a block-aligned prefix synchronously, then rejects the load:

```python

from typing import TYPE_CHECKING, Any
from vllm.distributed.kv_transfer.kv_connector.v1.base import (

@dataclass

class RogueSyncRejectConnector(KVConnectorBase_V1):

        super().__init__(vllm_config=vllm_config, role=role, kv_cache_config=kv_cache_config)

        self._need_load: dict[str, bool] = {}
        self._load_errors: set[int] = set()

        matched = ((n - 1) // self._block_size) * self._block_size
        new = matched - num_computed_tokens
        return (new, False) if new > 0 else (0, False)   # SYNC load

        for r in scheduler_output.scheduled_new_reqs:

                meta.reqs.append((r.req_id, list(r.block_ids[0])))
        self._need_load.clear()
        return meta

    def start_load_kv(self, forward_context, **kwargs):     # REJECT: load nothing
        meta = self._get_connector_metadata()
        for _rid, block_ids in meta.reqs:
            self._load_errors.update(block_ids)

    def get_block_ids_with_load_errors(self):
        errs, self._load_errors = self._load_errors, set()
        return errs

    def wait_for_layer_load(self, layer_name): return
    def save_kv_layer(self, layer_name, kv_layer, attn_metadata, **kwargs): return
    def wait_for_save(self): return
```

## Root cause (traced with per-step instrumentation)

### Part 1
worker side, affects both scheduling modes. In the V2 runner, `RequestState.num_computed_tokens` is a GPU-backed `StagedWriteTensor` alongside an optimistic CPU mirror (`num_computed_tokens_np`), and the GPU copy is advanced forward-only by `post_update_num_computed_tokens`. A recompute truncates `num_computed_tokens` backward, but `GPUModelRunner.update_requests` (`vllm/v1/worker/gpu/model_runner.py`) writes that only to the CPU mirror, so the GPU tensor stays stale. `prepare_prefill_inputs` and `prepare_pos_seq_lens` then read the stale GPU value and gather the recompute's input tokens and positions from the wrong offset. On the instrumented recompute step under sync scheduling, `num_computed=0` but `gpu_num_computed=19`, and `input_ids` is `[<3 tail tokens>, <16 uninitialized garbage>]` instead of the real prompt.

### Part 2
Scheduler side, async scheduling only. Under async scheduling the failed request has in-flight output frames reserved via `num_output_placeholders`, and `_update_requests_with_invalid_blocks` (`vllm/v1/core/sched/scheduler.py`) never rolls them back, so the recompute is scheduled with extra placeholder tokens (`num_scheduled = num_tokens + num_output_placeholders`) and appends garbage tokens past the prompt.

## Suggested fix

Two small changes. Both functions are byte-identical between 0.25.1 and `main`:

1. In `GPUModelRunner.update_requests`, when `num_computed_tokens` is a backward jump, push it to the GPU tensor with `num_computed_tokens.stage_write_elem` followed by `apply_write`.
2. In `_update_requests_with_invalid_blocks`, for each affected request, roll back `num_output_placeholders` and add `num_output_placeholders - 1` to `async_tokens_to_discard`. This mirrors the preemption handling in `reset_prefix_cache`.

Verified live (Qwen3-8B-AWQ, RTX 5090, V2 runner) and independently re-verified on a clean install. With both fixes, the reject-then-recompute output is byte-identical to the no-connector baseline under both `--async-scheduling` and `--no-async-scheduling`, with the recovery path confirmed to fire. A PR follows.

### Scope and caveats

- **Part 1** is precisely scoped: the backward-jump guard can only fire on the recompute path. Resumed and preempted requests take the V2 new-request path (they are not in `scheduled_cached_reqs`), and decode, chunked prefill, and spec decode advance `num_computed_tokens` strictly forward, so the `<` comparison never trips there. The staged GPU write does not collide with `post_update_num_computed_tokens` (a Triton kernel), and `apply_write` is idempotent and guarded.
- **Part 2**'s `num_output_placeholders - 1` is correct only when each in-flight frame carries one token. `num_output_placeholders` is incremented in tokens (`num_sampled_tokens_per_step + cur_num_spec_tokens`), but `async_tokens_to_discard` is consumed one per frame. So `- 1` is exact for the vanilla case and for pipeline parallelism, since the increment has no PP term. With speculative decoding or diffusion a frame carries `1 + k` tokens, so `- 1` over-discards by `k` and shifts the output. The proposed fix scopes correctness to the non-spec-decode and non-diffusion case; a general fix needs the true in-flight frame count. Note that simply zeroing the counter and discarding nothing would under-discard at pipeline-parallel depth greater than 1.
- Related and pre-existing: the same token-versus-frame conflation already exists in `reset_prefix_cache` (`async_tokens_to_discard = num_output_placeholders`, with the comment "1 + spec/PP frames"), which would likewise over-discard under speculative decoding.

## Workaround

Promise the load as asynchronous, so `get_num_new_matched_tokens` returns `(N, True)`. The request then parks in `WAITING_FOR_REMOTE_KVS` with `num_new_tokens=0`, so the tail is never forwarded before the load resolves, and a reject recomputes cleanly.
