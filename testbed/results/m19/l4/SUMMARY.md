연구자 지시 "커밋하고 해당 결정들을 전부 허용하는식으로 진행해"(2026-09-27). 규약은 `testbed/M16_PROTOCOL.md` 6절(4차 행)과 9절이다. 이 문서는 결과가 나오는 대로 채운다. 수치는 이 폴더의 결과 파일에서 옮긴다.

- 2회(`e2_early2/`, 그 뒤 준비된 8개 모델, 24회): broken·refused 0, pass 773, unknown 12. 실패 1회는 늘 빠지던 transformers FP8 조합이다.

**최종 실행 1(`e2/`, `d53ff10`, 38개 모델, 내려받기 없음):**
- 요약(`e2/E2_SUMMARY.md`): 유효 101회, 제외 8회. broken 실행 6회는 모두 토크나이저의 확인된 실제 차이다. 새 어댑터의 broken·refused 0, 근거 없는 해소 0, 해소 없는 실행의 출력 같음 96/97.
- 적재 점유율 중앙값은 16.3%(M18 5.0%)다. 비용 절의 9P 분석을 보라.
- **entail이 실행 하나를 깨뜨렸다: SGLang + Phi-3.5-mini-instruct.** 켬 실행이 첫 배치에서 CUDA illegal memory access로 죽었다. M18 E2의 켬 실행과 이번 끔 실행은 성공했다. 요약 도구는 json이 없는 실행을 세지 않아서 "깨뜨린 실행 0"으로 적었다. 이 줄이 그것을 바로잡는다.

**가르기(`bisect_phi35/`, `testbed/m19/bisect_phi35_sglang.sh`, `phi35_probe_steps.py`):**
- entail 상태별: 전체 켬은 두 번 모두 죽었다. Triton 훅을 빼도, 경로 점검만 켜도 죽었다. 경로 점검만 끄면(`ENTAIL_NO_PATHS=1`) 성공했고, 끔도 성공했다.
- entail 없이 같은 요청을 하나씩: 로그확률 없는 평범한 생성에서 이미 결과가 갈린다. story_a의 앞 32·64토큰은 성공했다. 128토큰은 flashinfer `VariableLengthMergeStates`의 "Unsupported head_dim: 96"으로 스케줄러가 멈췄다. 192·235토큰과 원문 글은 illegal memory access로 죽었다.
- 판정: 엔진의 실제 결함이다. SGLang 0.5.20이 head_dim 96 모델(Phi-3.5-mini)에 flashinfer를 고르는데, 상태 병합 경로가 그 head_dim을 받지 못한다. entail이 없어도 128토큰이 넘는 프롬프트에서 죽는다. E2의 짧은 프롬프트는 거기에 닿지 않는다. 그런데 시작 경로 점검의 탐침(119~235토큰)이 사용자의 첫 요청 전에 이 결함을 건드려 엔진을 멈췄다. 원칙 12 위반이다.
- 조치(entail `2aa975b`): SGLang은 시작할 때 prefill을 한 번도 돌리지 않는다. 그래서 탐침이 엔진의 첫 prefill이 된다. 이제 SGLang의 경로 점검은 `ENTAIL_PATHS=1`일 때만 돌리고, 그렇지 않으면 시작 경계에서 이유를 unknown으로 한 번 알린다. vLLM은 그대로 둔다. 시작할 때 모델의 forward(profile 실행)를 돌리고 attention 선택기가 head size를 검사하며, E2 38개와 S4에서 문제가 없었다.
**최종 실행 2(`e2_final/`, 동결 커밋 `2aa975b`의 E2):** transformers와 vLLM은 최종 실행 1의 것을 쓴다(`2aa975b`는 `sglang_paths.py`만 바꿨다). SGLang 38회는 `2aa975b`로 다시 돌렸다(`e2_sglang_2aa975b/`). 합친 과정은 `e2_final/README.txt`에 있다.
- 요약(`e2_final/E2_SUMMARY.md`): 실행 110, 유효 102, 제외 8. M18과 같은 수이고, 제외 8은 끔 실행도 실패한 조합이다.
- **entail이 깨뜨린 실행 0.** Phi-3.5 SGLang은 성공했고 출력도 같다.
- broken 실행 6은 모두 토크나이저의 확인된 실제 차이다. 새 어댑터의 broken·refused 0, 근거 없는 해소 0, 출력 같음 97/98(M18 97/98).
- unknown 결정은 114다(M18 80). 늘어난 34는 SGLang 실행마다 한 번 나오는 "경로 점검을 하지 않은 이유"다.
- 적재 점유율 중앙값(9P에서 import): 전체 9.9%, p90 32.5%. 엔진별로 transformers 22.0%(같은 모델의 M18 18.6%), vLLM 10.6%(2.8%), SGLang 5.2%(5.0%). vLLM의 증가는 시작 경로 점검이다. 사용자 조건의 비용은 2절의 리눅스 디스크 측정을 보라.
- **틀린 경보 수(규약 9절, 두 방식):** 2.3절 정의대로 세면 6회(TinyLlama와 tiny-random-Llama, 엔진 셋). 확인된 실제 차이를 빼면 0회다.

- 연구자가 허용한 "시작 경로 점검 기본 켬"에서 SGLang만 벗어난 것이다. 대안 둘은 DEFERRED에 적었다: (가) 탐침을 사용자의 첫 요청 뒤로 미루고, 엔진이 이미 돌린 길이 안에서만 탐침을 보낸다. (나) 능력표에 백엔드 × head_dim 행을 더해 적재 때 알리거나 해소한다. 예를 들어 triton 백엔드로 보낼 수 있다.

## 2. 비용

**S4: 요청 처리 속도, entail 전체를 켠 프로세스와 끈 프로세스(`s4/`, `testbed/m19_s4.py`):**
- 조건: vLLM 0.30.0 기본(compile + CUDA 그래프, FULL 캡처), Qwen3-4B bf16, 엔진 코어를 같은 프로세스에 둠. 64토큰 프롬프트, 새 토큰 128. 4라운드이고, 라운드마다 켬·끔·대조를 돌려 가며 잰다. 프로세스마다 5회 잰 중앙값을 쓴다.
- 결과(`s4/summary.json`, 라운드 중앙값): B=1 켬/끔 1.0007(대조/끔 0.9968), B=8 1.0028(0.9938), B=32 **1.0110**(1.0007). B=32는 4라운드 모두 켬이 느렸다(1.005, 1.014, 1.020, 1.008; `s4/run.log`). 내려받기가 도는 동안 잰 것이다.
- 출력: B=1은 12개 프로세스가 모두 같다. B=8과 B=32는 세 갈래로 나뉘는데, 갈래마다 켬·끔·대조가 섞여 있다. 따라서 엔진 자체의 프로세스 간 비결정성이고, entail이 바꾼 것이 아니다.
- 적재: 켬 23.5~24.0 s, 끔·대조 21.7~22.4 s(첫 켬 프로세스는 53 s). 시작 경로 점검을 포함해 약 1.7 s(8% 안팎)가 더 든다.

## 3. 동결

- **동결 커밋: entail `2aa975b`**(로컬, 푸시 안 함). `d53ff10`(M19 L3.3a~d)에 "SGLang 경로 점검은 요청할 때만"을 더한 것이다. 어휘는 v10(`READABLE_VERSIONS` 1~10)이다. 규약 `testbed/M16_PROTOCOL.md` 9절에 적었다.
- 동결 전에 고친 것은 하나다. entail이 엔진을 깨뜨린 실행(원칙 12, 1절). 틀린 경보를 고치려고 규칙을 바꾼 것은 없다. 토크나이저 6회는 확인된 실제 차이라서 그대로 둔다.
- S4와 비용 측정은 `d53ff10`에서 했다. `2aa975b`의 변경은 SGLang 경로 점검뿐이다. 그래서 S4(vLLM)와 vLLM 비용은 그대로 맞는다. SGLang의 "전체" 적재 비용은 이제 경로 점검 몫(+3.9 s)이 빠진 값이 된다. E2 SGLang 점유율 중앙값 5.2%가 그것이다.
