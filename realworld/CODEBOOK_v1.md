# 코드북 v1 (초안)

- 작성: 2026-09-23. 로드맵 5.1. 대규모 실증 연구(500건 이상)에서 이슈를 분류하는 규칙이다.
- 이 문서는 측정 도구다. 역할 계열의 비중이 얼마여야 한다는 기준은 두지 않는다.
- 판단이 갈리는 규칙(`RESEARCH_PLAN.md` 2.3절)은 하나로 정하지 않는다. 해당 사례에 표시를 달고, 결과를 좁은 계산과 넓은 계산으로 함께 낸다(7절).
- 파일럿 70건의 분류(`bug_labels_round1.json`)와 가설을 모르는 재분류(`reliability.json`, 카파 0.85)에서 출발했다.

## 1. 분석 단위와 포함 기준

- **단위:** GitHub 이슈 하나. 같은 결함의 중복 이슈는 대표 하나만 센다.
- **포함:** 추론 결과가 틀린 경우. 결과에는 텍스트, 로짓, 점수, 임베딩, 영상·음성, 도구 호출 인자가 모두 들어간다. 오류 메시지가 같이 났는지는 따지지 않는다.
- **제외:**
  - 충돌만 있는 경우, 성능만 문제인 경우, 기능 요청
  - 사용자의 잘못된 사용. 단, 잘못된 입력을 조용히 받아 틀린 답을 낸 경우는 포함한다.
  - 하드웨어 고장
  - 모델 자체의 품질 문제

## 2. 단계 A: 원인이 확인되었는가

- **확인됨:** 셋 중 하나에 해당한다.
  - 유지보수자가 원인을 명시했다.
  - 이슈에 연결된 PR이 병합되어 증상을 고쳤다.
  - 재현 코드와 수정 코드로 원인이 드러난다.
- **불명:** 원인 설명이 없이 닫혔거나, "다음 버전에서 고쳐짐"만 있는 경우. 불명은 비중 계산의 분모에서 뺀다.

## 3. 단계 B: 기전 부류

평가자에게는 중립적인 글자만 보여 준다. 이름과 가설은 알려 주지 않는다.

| 글자 | 부류 | 정의 |
|---|---|---|
| A | 부품 사이 사실의 어긋남 | 두 부품이 각자의 규약 안에서는 맞게 계산했다. 그런데 주고받은 값에 관한 사실(형식, 범위, 시점, 성질 등)을 서로 다르게 가정했다. 형태는 셋이다: 누락(전달되지 않거나 무시됨), 불일치(다르게 해석함), 시점 오류(엉뚱한 때에 읽거나 낡은 것을 재사용함) |
| B | 한 부품 안의 계산 오류 | 한 부품의 수식이나 알고리즘 자체가 틀렸다. 다른 부품의 가정과는 관계가 없다 |
| C | 수치 정밀도 | 논리 결함은 없고, 부동소수점 반올림, 오버플로, 불안정성 때문에 틀렸다 |
| D | 텍스트 처리 파이프라인 | 토크나이저, 대화 템플릿, 출력 파서의 결함 |
| E | 기타 | 위 넷에 들지 않는다. 짧은 설명을 붙인다 |

- 판단 순서: 먼저 "각 부품이 제 규약 안에서 맞았는가"를 본다. 그렇다면 A 후보다. 한 부품이 제 규약 안에서도 틀렸다면 B다.
- 버퍼를 읽고 쓰는 순서를 어긴 경합은 A에 넣고, 사실 종류는 TIME으로 한다. 파일럿과 같은 방식이다.

## 4. 단계 C: 사실 종류 (A일 때만)

`RESEARCH_PLAN.md` 2.2절의 사실 어휘 v0을 쓴다: LAYOUT, TIME, RANGE, PROPERTY, FRAME, REDUCTION, MAPPING, DTYPE, SPECIALIZATION, PRECEDENCE. 어디에도 맞지 않으면 NEW로 두고 짧은 이름을 제안한다.

함께 적을 것:
- **경계:** 사실을 만든 쪽 → 사실을 쓴 쪽. 예: 체크포인트 설정 → 로더
- **형태:** 누락 / 불일치 / 시점 오류

## 5. 단계 D: 증상과 조용함

- **증상:** 깨진 출력(뜻 없는 문자열, 깨진 영상·음성) / 그럴듯한 오답(정확도 하락, 틀린 값) / 설정이 무시됨 / 기타
- **조용함:** 틀린 결과가 나올 때 오류나 경고가 있었는가. 있음 / 없음 / 알 수 없음
- **발동 조건:** 장비, 기능 플래그, 길이, 몇 번째 대화인지, 배치 구성. 적힌 만큼만 적는다.

## 6. 판단이 갈리는 경우: 표시로 남긴다

| 표시 | 언제 다는가 | 기본 분류 | 넓은 계산에서 |
|---|---|---|---|
| `axis_in_component` | 한 부품 안에서 텐서의 엉뚱한 축으로 합산하거나 인덱싱했다 | B | A (LAYOUT) |
| `declared_pipeline_overridden` | 토크나이저 클래스나 템플릿이 체크포인트에 선언된 설정을 덮어썼다 | D | A (PROPERTY) |
| `in_dependency` | 결함이 의존 라이브러리 안에 있다 | 기전대로 분류 | 좁은 계산에서는 제외 |
| `closed_without_fix` | 수정 없이 닫혔지만 유지보수자의 원인 설명은 있다 | 원인 설명대로 분류 | 좁은 계산에서는 제외 |

## 7. 보고 방식

- 역할 계열 비중은 두 값으로 낸다. 둘 사이를 범위로 보고한다.
  - 좁은 계산: 6절 표시가 달린 사례를 A로 세지 않거나 제외한다.
  - 넓은 계산: 6절의 넓은 규칙을 적용한다.
- 조용함 비율은 A 안에서, 그리고 전체에서 각각 낸다.
- 사실 종류별 건수, 경계별 건수, 증상별 건수를 낸다.
- 두 평정자의 일치도(카파)는 단계 A, B, C마다 따로 낸다.

## 8. 평정자 지침 (가설을 모르는 평가자용)

- 평정자에게는 1~6절의 정의와 중립적인 글자만 준다. 이 연구의 가설, 목표, 파일럿 결과는 알려 주지 않는다.
- 이슈 본문, 댓글, 연결된 PR을 읽고 판단한다. 근거가 된 문장의 위치(댓글 번호나 PR 번호)를 함께 적는다.
- 확신이 없으면 "불명"이나 E를 고르고, 이유를 한 줄로 적는다.
