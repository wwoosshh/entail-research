# 실사용 경로 확인 (2026-09-22, RTX 4070 Ti, Qwen3-4B bf16, transformers 5.17, torch 2.14)

## 1. 기본 배치 생성에서 헤드 공유 사실의 값 (`hf_default_batched.py`)

조건: 컴파일 없음, 기본 DynamicCache, sdpa, 길이가 다른 프롬프트 8개(64~512토큰)를 왼쪽 패딩으로 묶어 `generate()`, 탐욕 생성 64토큰, 3회 중앙값. 평가 도구, 합성 데이터 생성, HF 백엔드 RL 롤아웃이 보통 이렇게 쓴다.

transformers 규칙: `use_gqa_in_sdpa`는 마스크가 없을 때만 SDPA의 헤드 공유(`enable_gqa`)를 쓴다. 코드 주석은 마스크가 있으면 "math 커널로 떨어진다"고 적고 있다. 그래서 패딩 마스크가 있는 배치에서는 매 층, 매 스텝 K와 V를 헤드 수만큼 복사한다.

| 경로 | generate 시간 | 생성 속도 | GPU 커널 시간: 행렬곱 / 복사·원소별 / 어텐션 |
|---|---|---|---|
| 배치 8, 패딩, 기본 | 3.23 s | 158.7 tok/s | 1,562 / 826 / 458 ms |
| 배치 8, 패딩, 공유 사실 전달 | 3.25 s | 157.5 tok/s | 1,664 / 454 / 348 ms |
| 배치 1, 패딩 없음, 기본 | 2.69 s | 23.8 tok/s | 1,237 / 188 / 24 ms |

- 공유 사실을 넘기자 복사·원소별 커널 시간이 826 ms에서 454 ms로, 어텐션이 458 ms에서 348 ms로 줄었다. GPU 작업은 약 13% 줄었다.
- 그러나 벽시계 시간은 그대로였다. 이 경로는 파이썬에서 커널을 하나씩 부르는 비용이 병목이라 GPU가 기다리는 시간이 길다. GPU 절약이 사용자에게 보이지 않는다.
- 탐욕 생성 결과는 8문장 모두 같았다.
- 공유 사실을 넘겨도 어텐션 커널은 math가 아니라 같은 memory-efficient 커널이었다. transformers의 규칙은 이 PyTorch 버전에서는 필요 이상으로 보수적이다. 오래된 전제 때문에 사실을 지우는 규칙이 라이브러리에 남아 있다.
- 결론: 컴파일 없이 쓰는 대부분의 사용자에게 의미 소거의 성능 손실은 파이썬 호출 비용에 가려져 보이지 않는다. 손실이 드러나는 것은 호출 비용을 없앤 뒤, 즉 torch.compile과 CUDA Graph를 쓰는 경로다. 4주차 E4에서 그 경로의 손실은 1.3~2.5배였다.

## 2. transformers 내장 FlexAttention 경로의 한 칸 초과, 보통 사용에서의 영향 (`diag_hf_flex_generate.py`)

- `generate(cache_implementation="static")`은 호출마다 새 정적 캐시를 만든다(`_prepare_static_cache`). 새 캐시는 0으로 차 있으므로 결함이 여는 한 칸은 항상 비어 있다.
- 채팅 템플릿을 씌운 프롬프트 3개(17, 19, 29토큰)로 탐욕 생성 48토큰을 비교했다. 17, 19토큰에서는 결함이 있는 경로, 고친 경로, sdpa가 모두 같은 48토큰을 냈다. 29토큰에서는 결함 경로와 고친 경로 모두 sdpa와 16번째 토큰에서 갈렸고, 둘끼리는 38번째에서 갈렸다. 어텐션 구현을 바꿀 때 생기는 수치 잡음과 같은 크기다.
- 결론: 보통의 `generate()`에서는 결함이 사실상 드러나지 않는다. 캐시를 비우지 않고 재사용하거나 위치를 되돌려 쓰는 경우에만 답이 바뀐다. 4주차 노트 7.2절의 비중을 이만큼 낮춰 읽어야 한다.
- 네 번째 프롬프트(긴 프롬프트)에서는 내장 FlexAttention 경로가 컴파일 단계에서 오류로 멈췄다. 디코드용 커널의 타일 크기(BLOCK_M=512)가 블록 크기 128로 나누어지지 않는다는 오류다. 조용한 오답은 아니지만, 이 경로가 실사용에서 안정적이지 않다는 증거다.

## 3. Gemma 2 어텐션 소프트캡이 기본 경로에서 버려지는가 (`check_gemma2_softcap.py`)

조건: 가중치를 받지 않고 작은 무작위 Gemma2 모델(2층)을 만들었다. 무작위 초기값은 어텐션 점수가 너무 작아 캡이 걸리지 않으므로, 질의와 키 가중치를 20배로 키워 점수 중앙값을 약 13.7로 만들었다. 같은 가중치와 입력으로 eager 경로와 기본 경로(sdpa)를 비교했다.

| 설정 | 기본 구현 | eager 대 기본 경로 최대 차이 | 최상위 토큰 일치 | 경고 |
|---|---|---|---|---|
| 소프트캡 없음 | sdpa | 0.00002 | 100% | 없음 |
| 소프트캡 1.0 | sdpa | 1.78 | 9% | 없음 |

- transformers 5.17에서 Gemma2의 기본 어텐션 구현은 sdpa이고, 이 경로는 소프트캡 설정을 경고 없이 무시한다. eager 경로만 캡을 적용한다.
- 실제 Gemma 2의 캡은 50이다. 실제 가중치에서 점수가 얼마나 자주 이 크기에 이르는지는 재지 못했다. 가중치가 사용 동의가 필요한 모델이라 받지 않았다. 따라서 실제 모델에서 답이 얼마나 달라지는지는 모른다. 확인된 것은 "모델 설정에 적힌 사실이 기본 경로에서 조용히 사라진다"는 점이다.
