# 실사용 타당성 점검: 4주차 결과는 실제 AI 사용자가 겪는 문제인가

> **2026-09-23 검증.** 비율(약 70%, 보수적 59%, 92% 조용함)은 계산이 재현되지만 점 값으로 쓸 수 없다. 규칙에 따라 55~89%다. 1차 분류는 가설을 아는 쪽이 했다(`reinvestigation/audit/bug_data_audit.md`).

- 작성일: 2026-09-22
- 질문(사용자): 4주차에 찾은 손실이 상용 서비스와 일반 GPU 사용에서도 생기는가. 실제로 사람들이 AI를 쓸 때 부딪히는 문제인가. 컴파일러가 잃는 약한 의미가 실사용에서는 사실 필요 없는 영역은 아닌가.
- 방법
  1. 실제 버그 기록: vLLM, SGLang, transformers, llama.cpp 저장소의 2025-01-01 ~ 2026-09-22 이슈를 같은 규칙으로 뽑아 원인을 분류했다(`bugs_*.md`). 읽기 전용 GitHub API만 썼다.
  2. 서빙 엔진 자료: 주요 엔진이 어텐션 정보를 어떻게 넘기는지, 새 어텐션 변형이 나올 때 무슨 일이 있었는지 공개 자료로 확인했다(`engines_notes.md`).
  3. 로컬 확인: 기본 transformers 사용 경로에서 손실이 드러나는지 직접 쟀다(`local_checks.md`).

## 1. 실제 버그 기록 파일럿 (저장소당 최근 고쳐진 출력 오류 25건, 합계 100건)

표본 규칙: 제목에 wrong, incorrect, garbage, gibberish, nonsense, accuracy, mismatch, "different output", corrupted, degraded 중 하나가 든 이슈를 모으고, 출력이 틀리는 내용인지 걸렀다. 그중 "completed"로 닫힌 것을 최근 닫힌 순서로 25건 골라 본문, 댓글, 수정 PR을 읽고 원인을 분류했다.

원인 분류:
- R1 의미 누락: 인자, 설정 값, 모델 성질이 조용히 무시되거나 커널까지 전달되지 않음
- R2 범위·위치 불일치: 유효 길이, 위치 번호, 오프셋, 캐시 인덱스가 어긋남
- R3 배치·순서·매핑 불일치: 차원 순서, 헤드 대응, 저장 형식, 스케일 형식을 구성 요소끼리 다르게 읽음
- R4 낡은 상태·시점 오류: 값을 엉뚱한 때에 읽거나 이전 상태를 재사용함
- N1 수치·커널 산술, N2 플랫폼·툴체인, N3 토크나이저·템플릿·샘플링
- N4 버그 아님·수정 없이 닫힘, N5 원인 판단 불가

R1~R4를 "역할 계열"로 본다. 각 구성 요소는 제 몫을 맞게 계산하지만, 값이 무엇을 뜻하는지가 구성 요소 사이에서 사라지거나 어긋나는 결함이다.

|---|---|---|---|---|---|

| llama.cpp | 176 | 21 | 11 (52%) | 43% | 11 / 11 |

- 원인이 확인된 70건 중 순수한 수치·커널 산술 결함(N1)은 3건(4%), 플랫폼·툴체인(N2) 7건, 토크나이저 등(N3) 8건, 판단 불가(N5) 2건이었다.
- 100건 중 30건은 "completed"로 닫혔지만 원인이나 수정이 확인되지 않았다(N4). 오답 보고의 상당수가 원인 규명 없이 닫힌다.
- 100건 전체에서 오류나 경고 없이 틀린 답이 나온 비율은 88%였다.
- 보수적 재분류는 각 조사가 제시한 가장 낮은 해석이다. 수정이 병합되지 않았거나 원인이 의존성에 있을 수 있는 사례를 역할 계열에서 뺀 값이다.
- 제목에 오답 관련 단어가 든 출력 오류 이슈만 21개월 동안 네 저장소에서 714건이었다. 다른 단어로 쓴 보고는 빠졌으므로 하한이다.

4주차 실험과 직접 겹치는 실제 사례:
- **범위 사실의 누락과 정렬 혼동 (vLLM #47300, PR #47332, 2026-07-05 병합):** Gemma 4 비전 모델이 FlashAttention-4 경로에서 긴 입력과 이미지가 있으면 완전히 엉뚱한 출력을 냈다. 마스크 함수가 있으면 커널이 자체 슬라이딩 윈도 적용을 끄는데, 그 마스크 함수에 윈도 조건이 빠져 있었다. 또 청크 안의 상대 질의 위치를 절대 위치처럼 썼다. 4주차 E5에 주입한 "무시된 sliding_window"와 "인과 정렬 혼동"이 실제 엔진에서 그대로 일어났다.
- **추측이 틀려 조용히 틀린 답 (vLLM #43602, PR #43617, 2026-05-27 병합):** Qwen3-VL을 기본 컴파일 서빙 경로로 돌리면 정확도가 크게 떨어졌다. 컴파일 워밍업 때 시각 입력이 비어 있어 그래프가 "시각 입력 없음"으로 특화됐고, 실제 요청이 그 그래프를 재사용하면서 시각 정보가 빠졌다. eager에서는 정상이었다. E2의 추측 실패가 멈춤이 아니라 조용한 오답으로 나타난 사례다.
- **값을 엉뚱한 때에 읽음 (llama.cpp #21726, PR #21736):** CUDA Graph 재사용 검사가 데이터 포인터만 비교하고 모양을 비교하지 않아 낡은 그래프가 재생됐다. 4주차 7.2절의 결함과 같은 "읽는 시점" 계열이다.
- **이미 합산된 값을 부분합으로 다시 합산 (SGLang #37187, #31699):** 한 구성 요소가 만든 값의 상태(복제본인지 부분합인지)를 다른 구성 요소가 다르게 읽었다.

해석의 한계:
- 분류 규칙과 가설을 아는 에이전트가 저장소마다 한 명씩 분류했고, 교차 검증은 없었다. 역할 계열 쪽으로 기울었을 위험이 있다. 근거 문구 6개를 원문과 직접 대조해 모두 확인했지만, 분류 판단 자체를 다시 검증한 것은 아니다.
- 표본은 제목 키워드와 최근 닫힌 순서로 정해졌다. 최근 몇 달에는 DeepSeek-V4, 하이브리드(Mamba 계열) 모델, 분리 서빙처럼 새 기능이 많았다.
- "역할 계열"은 넓은 범주다. 동기화 누락처럼 보통 동시성 버그로 부르는 사례도 R4에 들어갔다.

## 2. 성능 손실은 실사용에서 어디에 나타나는가

근거는 `engines_notes.md`의 출처 링크를 따른다.

| 사용자 집단 | 대표 도구 | 4주차의 의미 소거 손실 | 근거 |
|---|---|---|---|
| 상용 GPU 서빙 | vLLM, SGLang, TensorRT-LLM | 주 경로에는 없다. 길이, 페이지 표, 윈도, 소프트캡, 싱크를 커널에 직접 넘기도록 전문가가 손으로 만들었다. 헤드 공유도 복사 없이 처리한다. | engines 1.1~1.4 |
| 로컬 소비자 GPU | Ollama, LM Studio (둘 다 llama.cpp) | 있다. 유효 범위, 윈도, 청크, ALiBi, 희소 어텐션까지 매 배치 CPU에서 만든 큰 마스크로 넘긴다. 커널은 마스크를 훑어 구조를 다시 찾는 보완을 여러 번 추가했다. | engines 1.5, 5.4 |
| 평가, RL, 연구 | lm-evaluation-harness의 HF 백엔드, TRL GRPO의 기본 생성 | 코드에 있다. 컴파일 없이 쓰면 파이썬 호출 비용에 가려 보이지 않는다. 문서가 권하는 정적 캐시와 자동 컴파일 경로에서는 1.3~2.5배로 드러난다. | local_checks 1, engines 3 |
| 새 모델, 새 어텐션 변형 | 모든 엔진 | 있다. 그 사실을 받는 커널이 생길 때까지 느린 우회, 기능 제거, 조용한 오답이 이어진다. | engines 2 |

새 변형이 나왔을 때 실제로 있었던 일:

| 변형 | 있었던 일 | 걸린 시간 |
|---|---|---|
| Gemma 2 소프트캡과 슬라이딩 윈도 (2024-06) | vLLM이 소프트캡을 빼고 윈도를 무시한 채 문맥을 4K로 잘랐다 | 전체 문맥 지원까지 약 5개월 |
| Llama 4 청크 어텐션 | vLLM에서 설정 충돌로 청크 어텐션이 조용히 꺼졌다. 32K 검색 점수가 0.000이었고 수정 뒤 0.944 | 2025-07-23 수정 |
| DeepSeek MLA (2024-05) | vLLM과 llama.cpp가 MLA 없이 풀어 쓴 KV로 돌렸다 | vLLM 약 7개월, llama.cpp 약 10.5개월 |
| gpt-oss 어텐션 싱크 (2025-08) | llama.cpp 첫날은 느린 커널만 싱크를 지원했다. RTX 4090 프리필이 최대 3.99배 느렸다 | 3일 |
| 슬라이딩 윈도 (llama.cpp) | 마스크로 흉내 내는 방식이 2024-07부터 쓰였고, 메모리를 줄이는 실제 윈도 캐시는 나중에 들어왔다 | 요청 뒤 약 20개월 |
| 유지 부담 | vLLM의 어텐션 백엔드 44개, SGLang 27개. 여러 개가 특정 모델 전용이다 | 계속 |

llama.cpp에서 일어난 "재발견 대 선언"의 실제 판:
- CUDA 커널은 마스크를 훑어 전부 가려진 KV 구간을 건너뛰는 보조 패스를 추가했다. 부담은 1% 미만이고 이득은 최대 1.18배, RTX 4090에서는 1.02배였다. Metal과 Vulkan도 같은 방식을 따랐다.
- 작성자는 이 구조를 CPU에서 미리 계산할 수도 있지만 복잡도에 비해 가치가 없다고 판단했다.
- 이후 DeepSeek V4용으로 "토큰당 살아 있는 KV 최대 개수"라는 명시적 힌트를 넘기는 경로가 들어왔다. CPU에서 32K 깊이 1.19배, 524K 깊이 2.03배였다. 4주차 E3b에서 본 것처럼, 재발견과 선언의 차이는 보통 길이에서는 작고 긴 문맥에서 커진다.

사실을 직접 넘기는 쪽에도 비용이 있다:
- vLLM은 2024년 Llama 3 8B 기준으로 실행 시간의 29%를 스케줄링과 입력 준비에 썼다. 이후 V1에서 입력을 캐시하고 변경분만 적용하도록 바꿨다.
- Llama 4의 어텐션 정보를 한 스텝에 세 번 만들던 문제로 토큰당 약 2 ms가 더 들었다.
- FlashInfer의 계획 단계는 CPU에서 돌아 CUDA Graph에 넣을 수 없다. vLLM과 TensorRT-LLM은 어텐션을 컴파일러가 들여다보지 못하는 불투명한 연산으로 감싼다.
- 즉 전문가들은 사실을 손으로 넘기는 대신 그 사실을 매 스텝 관리하는 인프라를 따로 만들고 유지한다.

## 3. 로컬 확인

`local_checks.md` 참고.
- 컴파일 없이 쓰는 기본 배치 생성에서는 헤드 공유 사실을 넘겨도 체감 속도가 같았다. GPU 작업은 13% 줄었지만 파이썬 호출 비용이 병목이라 드러나지 않았다.
- transformers의 헤드 공유 금지 규칙("마스크가 있으면 math 커널로 떨어진다")은 PyTorch 2.14에서는 맞지 않았다. 오래된 전제가 사실을 지우는 규칙으로 남아 있다.
- 4주차 7.2절의 한 칸 초과 결함은 보통의 `generate()`에서는 수치 잡음 수준이었다.
- transformers 5.17에서 Gemma 2의 기본 어텐션 경로(sdpa)는 모델 설정의 어텐션 소프트캡을 경고 없이 버린다. 점수가 캡을 넘는 조건에서 캡을 적용하는 경로와 최상위 토큰 일치율이 9%였다. 실제 가중치에서의 영향 크기는 재지 못했다.

## 4. 판정

### 4.1 실제 사용자가 겪는 문제인가

**부분적으로 그렇다. 다만 4주차에 가장 크게 보였던 성능 손실보다 정확성 쪽이 실사용에서 더 분명한 문제다.**

- **성능, 주류 모델의 상용 서빙:** 겪지 않는다. 1.3~2.5배 손실은 vLLM, SGLang, TensorRT-LLM의 주 경로에서 전문가가 이미 손으로 없앴다. 이 영역에서 새 컴파일러가 속도로 이기기는 어렵다.
- **성능, 그 대가:** 겪는다. 새 변형마다 수일에서 수개월의 지연, 기능을 빼는 임시 우회, 조용히 꺼지는 기능, 수십 개의 어텐션 백엔드 유지가 그 대가로 공개 기록에 남아 있다.
- **성능, 로컬 소비자 GPU:** 겪는다. 다만 보통 길이에서는 작다. 가장 많이 쓰는 로컬 엔진이 의미를 마스크로 지우고 커널에서 다시 찾는다. 명시적 선언의 이득은 긴 문맥에서 커진다.
- **성능, 평가·RL·연구 도구:** 코드에는 있고, 최적화 경로를 켤 때 드러난다.
- **정확성:** 분명히 겪는다. 네 저장소에서 제목만으로 걸러도 21개월간 출력 오류 보고가 714건이었다. 원인이 확인된 70건 중 71%, 보수적으로 59%가 역할 계열이었다. 그중 92%는 오류나 경고 없이 틀린 답을 냈다. 4주차 E5에 주입한 실수와 같은 모양이 실제 엔진에서 2026년에도 일어났다.

### 4.2 컴파일러가 잃는 "약한 의미"는 실사용에 필요 없는가

- **약한 의미는 실제로 필요 없다.** 4주차의 "블록이 전부 유효한가 일부만 유효한가" 구분은 스텝의 1% 안팎이었다. 가드 검사와 컴파일 중 의미 복원도 실사용 성능에 거의 영향이 없다. 이 부분을 이점으로 내세우면 안 된다.
- **강한 의미는 필요하다.** 유효 범위와 윈도, 위치, 헤드 공유, 저장 형식과 스케일 형식, "이 값이 이미 합산됐는가", "이 버퍼가 언제 유효한가" 같은 사실이다. 실제 버그와 새 변형의 지연이 모두 여기서 나왔다.
- **성능 쪽 강한 의미는 주류 경로에서 이미 손으로 전달되고 있다.** 그래서 남은 가치는 속도 자체보다, 그 전달을 손 대신 문법으로 하는 데 있다. 새 변형이 나올 때의 지연과 구성 요소 경계의 오답을 줄이는 것이다.

### 4.3 연구 방향에 주는 함의

- 주류 모델의 디코드 속도를 이점으로 내세우지 않는다. 이미 풀린 문제다.
- 핵심 주장을 정확성으로 옮긴다. 모델 정의, 엔진, 커널, 체크포인트 사이의 경계에서 사실이 사라지거나 어긋나는 결함이 실제 출력 오류의 다수를 차지한다. 역할을 필수로 적고 검사하는 인터페이스가 이 부류를 줄인다는 것을 보여야 한다.
- 두 번째 주장은 새 변형의 지원 시간이다. 변형의 사실을 한 번 선언하면 맞고 빠른 경로가 함께 나와야 한다. FlexAttention이 가는 방향이고, 여기에 검사와 필수성을 더하는 것이 차별점이다.
- 다음 실험 제안: 이번에 모은 실제 역할 계열 버그 50건을 재연한다. 각 경계를 역할 타입 명세로 적었을 때 몇 건이 컴파일 단계에서 거부됐을지 센다. 이 수치가 조사 기반 컴파일러의 가치를 실제 데이터로 보여 줄 가장 직접적인 근거가 된다.

### 4.4 한계

- 버그 분류는 저장소마다 한 명의 에이전트가 했고 교차 검증이 없다. 근거 문구 6개는 원문과 대조했지만 분류 판단은 다시 검증하지 않았다.
- 표본은 제목 키워드와 최근 순서로 뽑혀 최근 새 기능(DeepSeek-V4, 하이브리드 모델, 분리 서빙)에 치우쳤을 수 있다.
- 엔진의 성능 근거는 PR과 문서의 수치를 옮긴 것이고 제가 재현하지 않았다.
- Gemma 2 소프트캡 누락의 실제 모델 영향은 재지 못했다.
