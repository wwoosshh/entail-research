# 실행 시점 RoPE 덮어쓰기: 측정 정의

2026-09-23, 결과를 보기 전에 적는다. 측정의 정의만 적고, 방향을 가르는 문턱은 두지 않는다.

## 1. 질문

Qwen3 모델 카드는 YaRN을 켜는 방법으로 두 가지를 안내한다. 하나는 `config.json`에 `rope_scaling`을 넣는 것이고, 다른 하나는 실행할 때 넘기는 것이다. vLLM에는 `--rope-scaling`, SGLang에는 `--json-model-override-args`를 쓰라고 적혀 있다. 설치된 vLLM 0.30.0에는 `--rope-scaling` 플래그가 없어서, 실행 시점에 넘기려면 `--hf-overrides`를 써야 한다.

설정 수준 조사(`entail/audits/override_probe.py`)에서 두 경로의 결과가 달랐다.

- `config.json` 경로로 넣으면 기준값 1,000,000이 유지된다.
- `hf_overrides`로 넣으면 YaRN은 켜지지만, 회전 임베딩 기준값이 10,000으로 바뀐다. vLLM의 `get_rope`는 `rope_theta`가 없으면 10,000을 기본값으로 쓴다.

이 실험은 그 차이가 출력에 무엇을 하는지 잰다.

## 2. 구성

공통 조건은 다음과 같다.

- 모델: Qwen3-4B, bf16
- 엔진: vLLM 0.30.0, transformers 5.17.0
- 디코딩: 탐욕(greedy), 시드 0
- 캐시: `enable_prefix_caching=False`, 한 스텝 토큰 256, 동시 시퀀스 64(메모리 때문)
- 길이: `max_model_len=3072`
- 실행: 구성마다 프로세스를 따로 띄운다.

| 이름 | 방법 | 설정 조사가 말한 기준값 |
|---|---|---|
| A | 손대지 않음 | 1,000,000, YaRN 없음 |
| B | `config.json`에 YaRN ×4 (기준 경로) | 1,000,000, YaRN |
| C | `hf_overrides`로 YaRN ×4 (실행 시점 경로) | 10,000, YaRN |
| D | `hf_overrides`로 `rope_theta=10000` | 1,000,000 (무시됨), YaRN 없음 |
| E | `config.json`에 YaRN ×4와 `rope_theta=10000` | 10,000, YaRN |

YaRN 값은 모델 카드 값 그대로다(`factor` 4.0, `original_max_position_embeddings` 32768).

## 3. 측정

- **M1: 교사 강제 NLL.** 문서 세 개의 토큰당 평균 음의 로그우도를 잰다. 문서는 영어 GPL-3 전문, 한국어 `RESEARCH_PLAN.md`, 파이썬 소스(transformers `modeling_gemma2.py`)다.
  - 각 문서를 2048토큰 조각으로 나누고, 앞 4조각을 쓴다.
  - vLLM의 `prompt_logprobs`로 잰다. 샘플링이 없으므로 결정적이다.
- **M2: GSM8K 정확도.** 테스트 앞 500문항을 쓴다.
  - 0-shot 채팅이고, 생각 모드는 끈다(`enable_thinking=False`). 최대 512토큰이다.
  - 답 추출은 `issue_track/gemma2_softcap/g2softcap.py`의 `extract_answer`와 같다.
  - B와 C는 짝지어 비교한다(McNemar 정확 검정).
- **M3: 토큰 동일성.** 구성 쌍마다 GSM8K 출력 500개 가운데 글자 단위로 같은 것의 수를 센다.
  - D와 A가 같으면 덮어쓰기가 무시된 것이다.
  - C와 E가 같으면 C의 차이가 "기준값 10,000 + YaRN" 때문이라는 뜻이다.
- **M4: 조용함.** 엔진 로그에서 `rope`가 들어간 WARNING 이상 줄의 수를 센다.

## 4. 해석의 정의

- **"피해"**: C가 B보다 M1이나 M2에서 나쁜 것을 말한다. 크기는 숫자로만 적는다.
- **"YaRN 자체 비용"**: A와 B의 차이를 말한다. 모델 카드가 짧은 글에서 성능이 떨어질 수 있다고 경고하는 부분이라, C의 피해와 섞지 않는다.
- **"해소"**: 같은 C 구성에 entail를 켜고 돌린 결과가 B와 토큰 단위로 같고, NLL도 같은 것을 말한다.

## 5. 추가 (2026-09-23, Qwen3 결과를 본 뒤, Llama 결과를 보기 전에 적는다)

Qwen3에서 C와 B의 출력이 500/500 같았다. 설정 조사는 "기준값 10,000"이라고 했는데, 틀린 결론이었다. 원인은 조사가 `get_rope`만 불렀다는 데 있다. vLLM의 `qwen3.py`와 `qwen2.py`는 `rope_theta`가 빠지면 `set_default_rope_theta(config, 1000000)`로 채운다. 이런 모델 파일은 전체에서 10개뿐이고, `llama.py`와 `qwen3_moe.py` 등은 채우지 않는다. 그래서 같은 질문을 Llama-3.2-3B-Instruct(`rope_theta` 500,000, llama3 스케일링)로 다시 잰다.

| 이름 | 방법 |
|---|---|
| LA | 손대지 않음 |
| LA2 | LA를 한 번 더 실행한다. 토큰 동일성의 실행 간 대조다. |
| LC | 체크포인트에 이미 있는 `rope_scaling`을 `hf_overrides`로 똑같이 다시 넘긴다. |
| LE | `config.json`의 `rope_theta`를 10000으로 바꾼다. 기준값 10,000이 무엇을 하는지 보는 기준이다. |
| LC_rolecheck | LC와 같고, 해소기(`rope_alias`)만 켠다. |

- **LC:** 있는 값을 다시 말했을 뿐이므로, LA와 다르다면 그 차이는 전부 잃어버린 값 때문이다.
- **해석:** LC가 LE와 같고 LA와 다르면 코드 읽기가 맞다. LC_entail가 LA와 같으면 해소된 것이다.
- **측정:** M1~M4는 Qwen3와 같다. 기준으로 쓸 실행 간 변동은 LA와 LA2의 차이다.

## 6. 대조 결과가 바꾼 판정 방법 (2026-09-23, Llama 결과 전)

같은 구성 A를 두 번 돌렸다(A2). GSM8K 출력은 **253/500**만 같았다. NLL 차이는 0.0009 이하였고 정확도 차이는 0이었다. 이 설정의 vLLM은 실행할 때마다 배치 구성이 달라지고, 그래서 수치가 조금씩 달라진다. 결국 **실행 사이의 토큰 동일성은 "같은 모델"을 판정하는 근거가 되지 못한다.**

그래서 판정 방법을 다음처럼 바꾼다.

- **"같다":** 두 실행의 NLL 차이가 대조(A와 A2, LA와 LA2)의 차이와 같은 수준이고, 정확도 차이가 McNemar 검정에서 유의하지 않은 경우다. 토큰이 500/500 같으면 더 강한 증거로 적는다.
- **"다르다":** NLL 차이가 대조의 차이보다 몇 자릿수 크거나, 정확도 차이가 유의한 경우다.
- **해소:** C_entail와 B, LC_entail와 LA를 위 기준으로 비교한다.

## 7. SGLang에서 같은 질문 (정의는 `sglang_llama.py`에 SA를 돌리기 전에 고정했다. 이 절은 SA가 끝난 뒤, 나머지 결과 전에 옮겨 적었다)

엔진은 SGLang 0.5.20(transformers 5.12.1)이고, 모델은 Llama-3.2-3B-Instruct다. 실행 시점 경로는 `--json-model-override-args`다.

| 이름 | 방법 |
|---|---|
| SA, SA2 | 손대지 않음. SA2는 실행 간 대조다. |
| SC | 체크포인트의 `rope_scaling`을 `json_model_override_args`로 그대로 다시 넘긴다. |
| SE | `config.json`의 `rope_theta`를 10000으로 바꾼다. 기준값 10,000이 무엇을 하는지 보는 기준이다. |
| SC_rolecheck | SC와 같고, 해소기(`rope_alias`)만 켠다. |

- **M1:** NLL. 같은 문서 세 개를 쓰되 1024토큰 조각으로 나누고 문서당 4조각을 쓴다. 요청은 하나씩 보낸다. 조각 길이가 vLLM(2048)과 달라서 vLLM 수치와 직접 비교하지 않는다.
- **M2:** GSM8K 앞 200문항, 탐욕 디코딩, 최대 384토큰.
- **CUDA 그래프는 끈다.** 켜면 이 카드에서 그래프를 잡는 동안 메모리가 바닥났다(가용 0.00 GB, 크기 하나에 8초). 첫 시도는 그래서 멈췄고, 결과는 남기지 않았다.
- **해석:** 기준은 5·6절과 같다. SC가 SE와 같고 SA와 다르면 SGLang `llama.py`의 대체값(10,000) 때문이다.

## 8. 측정 문서 하나가 살아 있는 파일이었다 (2026-09-23 기록)

M1의 한국어 문서는 `RESEARCH_PLAN.md`를 그대로 읽고 있었다. 이 파일은 실행이 이어지는 동안에도 고쳐졌다.

- **실행 묶음 안의 비교는 영향이 없다.** vLLM 묶음(10:57~11:24)과 SGLang 묶음(11:26~11:31) 안에서는 파일이 바뀌지 않았다. 5~7절의 판정은 모두 같은 묶음 안의 비교다.
- **드러난 경위.** 라이브러리 이름을 바꾼 뒤 돌린 `SC_entail`은 GSM8K 출력이 SA와 200/200 같았다. 영어와 코드의 NLL도 같았는데, 한국어 NLL만 3.8655에서 3.8449로 달랐다.
  - 그 직후 손대지 않은 구성을 다시 돌렸다(`SA_now`). 세 문서 NLL이 모두 `SC_entail`과 같았다.
  - 그러므로 차이는 문서가 바뀐 탓이고, 라이브러리의 탓이 아니다.
- **고친 것.** 이후 실행은 고정한 사본 `data/korean_doc_2026-09-23.md`을 읽는다. 이 사본은 기록 시점의 `RESEARCH_PLAN.md`다. 앞선 실행들이 읽은 판과는 다를 수 있으므로, 앞선 수치와 한국어 NLL을 직접 이어 비교하지 않는다.
