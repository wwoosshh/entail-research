# Production GPU inference compilers and the 2025–2026 shift (research date 2026-09-22)

## 1. TensorRT (classic AOT graph compiler)
- Closed core, open shell: public repo "contains the Open Source Software (OSS) components of NVIDIA TensorRT" (plugins, ONNX parser, samples). https://github.com/NVIDIA/TensorRT
- Engine build time: ORT TRT EP docs: "Building engine involves exhaustive profiling for every kernels to select the optimal one"; example 384 s (no cache) vs 42 s (timing cache) vs 9 s (engine cache). https://onnxruntime.ai/docs/execution-providers/TensorRT-ExecutionProvider.html
- Per-GPU / per-version non-portability: "Each engine is created for specific settings such as model path/name, precision, workspace, profiles etc, and specific GPUs and it's not portable"; issue #977 (Dec 2020) "Serialized engines are not portable across platforms… or TensorRT versions" https://github.com/NVIDIA/TensorRT/issues/977 ; #2624 (Jan 2023) deserialization failures 8.4.2.2 vs 8.5.3.1 in NVIDIA's own Maxine SDK. https://github.com/NVIDIA/TensorRT/issues/2624 ; FAQ on cross-version reuse: "By default, no."
- Dynamic-shape optimization profiles: explicit min/opt/max; "if input shapes are out of range, profile cache will be updated ... and engine will be recreated" (rebuild at serving time). TensorRT-RTX 1.2: "Potential performance degradation for dynamic shapes due to data race in CUDA graph capture"; background kernel compilation "is opportunistic, not guaranteed." https://docs.nvidia.com/deeplearning/tensorrt-rtx/latest/getting-started/release-notes-1/1.2.html
- Unsupported layers / plugin churn: TensorRT 11.0.0 (May 27, 2026) removed entire `IPluginV2` family, dropped bundled plugins, static libraries. https://docs.nvidia.com/deeplearning/tensorrt/latest/getting-started/release-notes-11/11.0.0.html
- INT8 calibration: #3708 (Mar 2024): INT8 "gave severely distorted results" for EfficientViT-SAM despite 10,000 calibration images. https://github.com/NVIDIA/TensorRT/issues/3708 ; TensorRT 11.0.0 removed implicit quantization entirely: "The `IInt8Calibrator` class and all subclasses… have been removed. Use explicit quantization with Q/DQ nodes instead"; strongly-typed networks default.
- Compiler regressions: 11.3.0 (Sept 8–9, 2026) fixes "transformer model slowdowns from TensorRT 11.x", adds FP32-accumulation option for FP16 fused attention; still lists "Strongly typed FP16 DeBERTa shows 16-20% GPU time increase", build failures for SDXL UNetXL and FLUX.1-dev. "TensorRT 10.7 was the last release that supported DLA." https://docs.nvidia.com/deeplearning/tensorrt/latest/getting-started/release-notes-11/11.3.0.html
- Debugging: bisection with Polygraphy; no kernel-level source.
- 2025–2026 products:
  - TensorRT for RTX (June 12, 2025): "a drop-in replacement for NVIDIA TensorRT" for consumer RTX, AOT + JIT specialization on end-user GPU; <200 MB; AOT <15 s; "Shape-specialized kernels can be generated on the fly… compiled in a background thread while initial inference requests are serviced using fallback kernels." Plugins not supported. https://developer.nvidia.com/blog/run-high-performance-ai-applications-with-nvidia-tensorrt-for-rtx/
  - TensorRT Edge-LLM (Jan 8, 2026): open-source C++ runtime for Jetson/DRIVE Thor using classic AOT engines (HF → ONNX → engine), EAGLE-3, NVFP4; "embedded inference requires a dedicated, tailored solution". https://developer.nvidia.com/blog/accelerating-llm-and-vlm-inference-for-automotive-and-robotics-with-nvidia-tensorrt-edge-llm/
  - Model Optimizer: 0.25 Blackwell FP4 PTQ/QAT (Mar 18, 2025); 0.45.0 (Jul 6, 2026) NVFP4 W4A16, MXFP4→NVFP4; 0.47.0 (Sept 2026) per-expert MoE quantization. https://nvidia.github.io/Model-Optimizer/reference/0_changelog.html
  - Cadence: 10.9 (Mar 2025) … 10.14.1 (Nov 2025); 11.0.0 May 27, 2026; 11.3.0 Sep 9, 2026 (Vera Rubin CC 10.7 in Enterprise).
- Declining for LLMs? Datacenter: yes — NVIDIA's own LLM stack made PyTorch default (Sept 2025) and deleted TensorRT engine backend in TRT-LLM 1.2 (Mar 2026). TensorRT engines survive at edge (Edge-LLM), client RTX (TRT-RTX), non-LLM vision/diffusion. Secondary 2026 commentary: vLLM "almost always the default choice" on NVIDIA. https://builderai.tools/blog/state-of-open-source-llm-inference-engines-2026

## 2. TensorRT-LLM: PyTorch-backend pivot
- Timeline: PyTorch backend introduced 0.17.0 (Jan 30, 2025) "to enhance the usability of the system and improve developer efficiency"; AutoDeploy experimental 0.19 (May 9, 2025); **1.0.0 (Sep 24, 2025): "Promote PyTorch to be the default LLM backend"** (breaking change), "the LLM API is now stable" https://github.com/NVIDIA/TensorRT-LLM/releases/tag/v1.0.0 ; **1.2.0 (Mar 12, 2026): TensorRT backend removed** — `LLM(backend="tensorrt")` raises ValueError; `trtllm-build`/`trtllm-refit`/`trtllm-prune`, per-model `convert_checkpoint.py`, TensorRT pip dependency gone; "HuggingFace checkpoints load directly." https://nvidia.github.io/TensorRT-LLM/legacy/tensorrt-backend-removal.html
- NVIDIA's reasons: "TensorRT LLM is designed to be modular and easy to modify. Its PyTorch-native architecture allows developers to experiment with the runtime or extend functionality." https://nvidia.github.io/TensorRT-LLM/overview.html ; AutoDeploy blog (Feb 9, 2026): "Deploying a new architecture traditionally requires significant manual effort"; "Every new LLM architecture comes with its own inference challenges." https://developer.nvidia.com/blog/automating-inference-optimizations-with-nvidia-tensorrt-llm-autodeploy/
- Implication: value now "custom kernels for common inference operations (attention, GEMMs, MoE, ...)"; NVIDIA "actively releasing its most performant LLM inference kernels" from TRT-LLM into FlashInfer (Jun 13, 2025) https://developer.nvidia.com/blog/run-high-performance-llm-inference-kernels-from-nvidia-using-flashinfer/ ; kernel layer increasingly JIT: DeepGEMM "All kernels are compiled at runtime through DeepJIT", cuDNN runtime fusion, FlashInfer JIT templates.
- torch.compile inside TRT-LLM: "mainly relies on torch.compile fullgraph mode" for piecewise CUDA graphs; only `num_tokens` dynamic; attention eager between pieces. https://nvidia.github.io/TensorRT-LLM/features/torch_compile_and_piecewise_cuda_graph.html ; PR #18366 (Sept 2026): "Enabling torch.compile… often results in a large increase in startup times": Qwen3-8B FP8 TP1 startup ~53 s (off) → ~115 s (on) → ~93 s w/ piecewise-only. https://github.com/NVIDIA/TensorRT-LLM/pull/18366
- AutoDeploy: torch.export → core ATen + custom ops → pattern-match MoE/attention/RoPE/SSM → sharding/KV cache/quantization → torch.compile + CUDA graphs; beta; "over 100 text-to-text LLMs"; "AutoDeploy enables the shift from manually reimplementing and optimizing each model toward a compiler-driven workflow."
- Remaining complaints: dev image ~63 GB disk https://nvidia.github.io/TensorRT-LLM/installation/build-from-source-linux.html ; requires CUDA 13.1 + aligned PyTorch, pip may silently replace PyTorch with incompatible build; "PyTorch backend on SBSA is incompatible with bare metal environments like Ubuntu 24.04".
- vLLM/SGLang comparison: vLLM V1 (Jan 27, 2025) torch.compile + piecewise CUDA graphs to "efficiently support a wide variety of models while minimizing the need of writing custom kernels" https://vllm.ai/blog/2025-01-27-v1-alpha-release ; five CUDA-graph modes, default FULL_AND_PIECEWISE. FlashInfer integrated in "SGLang, vLLM and MLC-Engine". https://arxiv.org/abs/2501.01005
- Market indicators: vLLM stars 14k→32.6k, contributors 190→740 during 2024; Amazon Rufus, LinkedIn; 46,500+ stars, 1,000+ contributors on joining PyTorch Foundation (May 6, 2025) https://pytorch.org/blog/pytorch-foundation-welcomes-vllm/ ; SGLang: "trillions of tokens in production each day," "Over 400,000 GPUs," adopters xAI, NVIDIA, AMD, Intel, LinkedIn, Cursor, Oracle/Google/Azure/AWS, Baseten, Baidu, Alibaba, Tencent https://github.com/sgl-project/sglang ; NVIDIA Dynamo treats TRT-LLM, vLLM, SGLang as peer backends.

## 3. ONNX / ONNX Runtime
- Opset lag: ONNX 1.18 (opset 23) May 12, 2025; 1.19 (24) Aug 27, 2025; 1.20 (25) Dec 1, 2025; 1.21 (26) Mar 27, 2026; 1.22 (27) Jun 15, 2026; 1.23 (28) Sep 18, 2026. ORT 1.28.0 (Jul 25, 2026) added opset 26 (~4 months after); 1.29.0 (Aug 17, 2026) opsets 26–27. PyTorch exporter default opset 18→20 only in 2.9 (Oct 15, 2025). https://pypi.org/project/onnx/#history
- Exporter breakage: `dynamo=True` default flip (issue #151693, Apr 18, 2025) shipped in 2.9; removed `torch.onnx.dynamo_export`, `onnxrt` compile backend; legacy fallback removed 2.11 (Mar 23, 2026). Post-flip bugs: #168969 (Nov 24, 2025) Embedding+LSTM+Linear fails; #170172 (Dec 11, 2025) dynamo exporter "hardcodes the output batch dimension to 1, completely ignoring the dynamic_axes parameter" when model has buffers, breaking TensorRT deployment; workaround "unsustainable". https://github.com/pytorch/pytorch/issues/170172
- EP churn: ROCm EP "removed since 1.23 release. Please Migrate your applications to use the MIGraphX Execution Provider" (Sep 25, 2025) https://onnxruntime.ai/docs/execution-providers/ROCm-ExecutionProvider.html ; DirectML "in sustained engineering… new feature development has moved to WinML"; Windows ML lists it "(legacy)": "no new operator coverage, no new hardware-specific optimizations, and no major performance investments are planned" (Aug 5, 2026) https://learn.microsoft.com/en-us/windows/ai/new-windows-ml/webgpu-ep ; Windows ML 2.x downloads vendor EPs on demand: MIGraphX ("not supported for GenAI scenarios today"), NvTensorRtRtx, OpenVINO, QNN, VitisAI, WebGPU (experimental). WebGL/JSEP deprecated 1.29.0.
- ORT GenAI still 0.x: 0.9.0 Aug 6, 2025 → 0.16.0 Sep 13, 2026. Core ORT: PagedAttention w/ quantized KV, NVFP4 QMoE, cuDNN SDPA (1.29.0); speculative decoding + INT4 paged KV (1.30.0, Sep 10, 2026). https://pypi.org/project/onnxruntime-genai/#history
- Losing relevance for LLMs? Datacenter: yes — TRT-LLM, vLLM, SGLang load HF checkpoints directly, never touch ONNX; ORT GenAI pre-1.0, aimed at Windows/mobile/web. ONNX persists as intake format for AOT edge/client compilers (Edge-LLM, TRT-RTX EP-context, QNN, OpenVINO EP).

## 4. Other GPU/edge compilers
- Intel OpenVINO: 2025.0 (Feb 6, 2025) → 2026.4.0 (Sep 16, 2026). GPU correctness: issue #37419 (Aug 13, 2026; OV 2026.3.0; Arc 140V/Xe2) INT4 LLM "compiles, warms up, and generates without any error — but the output is numerically wrong" while identical IR correct on CPU https://github.com/openvinotoolkit/openvino/issues/37419 ; OVMS 2025.3 GPU terminates silently on first chat completion (Dec 11, 2025). INT4 KV-cache compression on GPU (2026.2.0); removals: Model Optimizer/`openvino-dev`.
- Apple MLX: "Computations in MLX are lazy"; `mx.compile` recompiles on any change in shape, dtype, number of inputs; "can't evaluate arrays… inside compiled functions". https://ml-explore.github.io/mlx/build/html/usage/compile.html ; CUDA/Linux backend `pip install mlx[cuda]`. Core ML (secondary): "compute graph is largely fixed at conversion time, dynamic shapes are awkward"; MLX "targets the GPU (not the ANE today)".
- Qualcomm QNN: "QNN EP does not support models with dynamic shapes"; HTP requires quantized models; "Loops and Ifs are not supported"; context binaries per SoC not transferable. https://onnxruntime.ai/docs/execution-providers/QNN-ExecutionProvider.html
- Arm KleidiAI: CPU micro-kernels; "API modifications, including function name changes… may occur without advance notice".
- Android: NNAPI "deprecated in Android 15"; Google: transformers/diffusion meant "developers needed tools and infrastructure that update frequently"; migrate to LiteRT + GPU delegate. https://developer.android.com/ndk/guides/neuralnetworks/migration-guide ; LiteRT-LM v0.16.0 production in Chrome/Chromebook Plus/Pixel Watch.
- WebGPU/WebNN: WebNN Candidate Recommendation Draft (Sept 10, 2026); implementation "experimental" behind flags, 95 ops. https://www.w3.org/TR/webnn/ ; ORT Web WebGPU graph capture only for static-shape models.

## 5. Serving-time compilation trends
- CUDA graphs vs torch.compile vs static engines: vLLM modes NONE/PIECEWISE/FULL/FULL_DECODE_ONLY/FULL_AND_PIECEWISE; TRT-LLM adopted same piecewise pattern but pays startup; TRT-RTX AOT+JIT w/ background shape-specialized kernels. Apr 25, 2026 paper formalizes hybrid: static via CUDA-graph replay, dynamic via JIT kernels, up to 66% TTFT reduction. https://arxiv.org/abs/2604.23467
- JIT at serving time and its cost: FlashInfer "customizable attention template… through Just-In-Time (JIT) compilation"; DeepGEMM DeepJIT (SM90 FP32 scales vs SM100 packed UE8M0). **Incident vLLM #56684 (Sep 13, 2026; DeepSeek-V4.1-Flash on 8×B200): 3.4 s engine stalls because DeepGEMM "JIT-compiles a new sm100_fp8_gemm_1d1d kernel for each configuration it has not met," 3–3.6 s nvcc each, mid-serving; fix = pad to 1024-token buckets + precompile at warm-up; compiles invisible to `jit_monitor`.** https://github.com/vllm-project/vllm/issues/56684 ; cuDNN: "runtime fusion engines generate the kernel (or kernels) at runtime based on the graph pattern". https://docs.nvidia.com/deeplearning/cudnn/latest/developer/graph-api.html
- Spec decoding / disaggregation: vLLM uniform decode batches become query length "1+num_spec_tokens"; cascade attention forces PIECEWISE. TRT-LLM 1.1 KV Cache Connector API for disaggregation.
- NVIDIA Dynamo (Mar 18, 2025): serving framework, not compiler; disaggregated prefill/decode, KV-aware router; backends TRT-LLM, vLLM, SGLang. Pushes compiler problem down to each backend.

## 6. Quantization-format churn as compiler burden
- Formats: MX (Oct 16, 2023, Intel/NVIDIA/Microsoft) https://arxiv.org/abs/2310.10537 ; NVFP4 (Jun 24, 2025): E2M1 w/ 16-element blocks + E4M3 scales vs MXFP4 32-element blocks + E8M0 scales; at launch TRT-LLM full, vLLM "early," SGLang "upcoming". https://developer.nvidia.com/blog/introducing-nvfp4-for-efficient-and-accurate-low-precision-inference/
- Stack lag: TRT-LLM NVFP4 from 0.17 (Jan 2025), MXFP4 from 1.0 (Sep 2025). vLLM gpt-oss MXFP4 day-0 (Aug 5, 2025) required three different kernels — FlashInfer MoE on Blackwell, OpenAI Triton `matmul_ogs` on Hopper, Triton on AMD. https://vllm.ai/blog/2025-08-05-gpt-oss ; SGLang (Sept 2026): NVFP4 native only SM100/103, MXFP4 unsupported on NVIDIA but supported AMD CDNA3/4 and Ascend. https://docs.sglang.io/advanced_features/quantization.html
- Per-SKU gaps: TRT-LLM matrix: consumer Blackwell SM120 lacks FP8 block-scale, all INT4 AWQ/GPTQ, NVFP4 KV cache; Ampere no FP8 GEMM; "FP8 block wise scaling GEMM kernels for sm100/103 are using MXFP8 recipe… slightly different from SM90 FP8 recipe". https://nvidia.github.io/TensorRT-LLM/features/quantization.html ; DGX Spark (GB10/SM121, Dec 1, 2025): "FP4 is not properly utilized in current VLLM builds on our hardware", AWQ ~32% faster than NVFP4; CUTLASS MXFP4 MoE SM121 kernels merged Feb 16, 2026, fixes Mar 2026 → NVFP4 led AWQ ~20%. https://forums.developer.nvidia.com/t/psa-state-of-fp4-nvfp4-support-for-dgx-spark-in-vllm/353069
- FP8: vLLM W8A8 needs CC ≥ 8.9; Turing/Ampere weight-only W8A16 via Marlin. Scale-format divergence Hopper vs Blackwell forces separate kernel paths.
- ORT 1.29.0 NVFP4 QMoE (Aug 2026); Model Optimizer MXFP4→NVFP4 (Jul 2026) — a year after NVFP4 launch.
- Accuracy format-specific (Mar 5, 2026): "MLP up- and down-projection layers consistently dominate in terms of sensitivity"; "early blocks can be highly sensitive, particularly under MXFP4". https://arxiv.org/abs/2603.08747
- FP6: no production-stack support found.

## Fundamental vs. transient
| Problem | Class | Why |
|---|---|---|
| Engines tied to GPU/driver/TRT version | Fundamental to AOT autotuning; mitigated by TRT-RTX JIT, version-compat, EP-context | |
| Dynamic shapes vs static kernel selection (profiles, CUDA-graph buckets, QNN static-only, `num_tokens`-only, MLX recompiles) | Fundamental | Static specialization is where speed comes from |
| Architecture velocity outrunning op coverage (unsupported layers, opset lag, exporter breakage, per-model reimpl) | Fundamental (structural) | Reason NVIDIA gave for PyTorch-native TRT-LLM/AutoDeploy; Google for NNAPI deprecation |
| Quantization-format churn per HW gen (FP8→NVFP4/MXFP4; scale formats; per-SKU gaps) | Fundamental while each gen ships new numerics | 3–12 months lag per stack |
| JIT-at-serving-time stalls | Fundamental trade-off, transient per instance | |
| Closed-source core / debugging by bisection (TensorRT) | Fundamental (vendor policy) | |
| Edge fragmentation (per-SoC binaries, vendor delegates, ANE inaccessible) | Fundamental | |
| INT8 calibration pain | Transient (resolved by removal) | |
| TRT 11 API breaks, TRT-LLM backend removal, ORT EP reshuffle, NNAPI→LiteRT | Transient migration churn, recurring every 2–3 years | |
| Specific bugs | Transient | |
| ORT GenAI 0.x, WebNN CR-draft, LiteRT-LM preview | Transient (maturation) | |
