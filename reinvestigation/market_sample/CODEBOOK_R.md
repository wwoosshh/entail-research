# 재조사 코드북 (평정자용)

- 작성: 2026-09-23, 사례 기록을 보기 전에 썼다.
- 평정자에게는 이 문서의 1~4절만 준다. 5절(집계 정의)과 연구의 가설은 알려 주지 않는다.
- 옛 코드북(`realworld/CODEBOOK_v1.md`)과 달리, 부품 사이 문제를 세 글자(B, C, D)로 나눴다. 한 글자가 너무 넓어 무엇이든 담기는 일을 줄이고, 평정자가 가장 구체적인 기전을 고르게 하려는 것이다.

## 1. 입력

사례 기록 하나는 GitHub 이슈 하나를 정리한 것이다. 필드는 다음과 같다.
- 증상(symptom)
- 원인 설명(root_cause)
- 관련 부품(components_involved)
- 수정(fix)
- 근거 URL(evidence_urls)

기록이 부족하면 근거 URL을 직접 읽어도 된다. GitHub은 읽기만 한다.

## 2. 단계 1: 대상인가

다음 두 조건을 모두 만족하면 대상(`eligible: yes`)이다.
- 소프트웨어가 틀리거나 품질이 떨어진 출력을 냈다. 출력에는 텍스트, 로짓, 이미지, 음성, 임베딩, 도구 호출 인자가 모두 들어간다.
- 원인이 유지보수자의 설명, 병합된 수정, 또는 재현과 수정으로 확인됐다.

어느 하나라도 아니면 `eligible: no`로 하고 이유를 한 줄 적는다.

## 3. 단계 2: 기전 (대상일 때만, 가장 잘 맞는 글자 하나)

| 글자 | 정의 |
|---|---|
| A | 한 부품 안의 계산이 그 부품 자신의 명세에 비추어도 틀렸다. 수식, 알고리즘, 인덱스 계산, 분기 조건의 잘못이 여기에 든다. |
| B | 두 부품, 또는 한 부품의 두 곳이 주고받은 값·설정·상태의 뜻을 서로 다르게 가정했다. 각자는 자기 가정 안에서 맞게 계산했다. 뜻에는 형식, 단위, 메모리 배치, 위치 기준, 유효 범위, 성질, 이름이 들어간다. |
| C | 넘겨야 할 값·설정·정보가 중간에서 전달되지 않았다. 또는 받는 쪽이 받고도 쓰지 않았다(무시, 버림, 기본값으로 대체). |
| D | 값이나 상태를 읽고 쓰는 시점이 어긋났다. 낡은 값의 재사용, 준비되기 전에 읽음, 동시 접근 경합, 캐시나 그래프를 다시 쓰는 조건의 오류가 여기에 든다. |
| E | 수치 정밀도 문제다. 논리는 맞지만 부동소수점 반올림, 오버플로, 누적 오차, 비결정성 때문에 틀렸다. |
| F | 텍스트나 입력의 전처리 결함이다. 토크나이저, 대화 템플릿, 프롬프트 처리, 출력 파서가 여기에 든다. |
| G | 외부 요인이다. 하드웨어, 드라이버, 벤더 라이브러리(cuBLAS 등), 서드파티 의존성 내부의 결함이 여기에 든다. |
| H | 사용자 설정이나 사용법의 문제다. 소프트웨어는 문서대로 동작했다. |
| I | 배포된 모델 파일이나 가중치 자체가 잘못됐다. |
| J | 기타. 짧은 설명을 붙인다. |

판단 순서:
1. 결함이 소프트웨어 밖(G, H, I)인지 먼저 본다.
2. 소프트웨어 안이면, 한 부품이 자기 명세로도 틀렸는지(A)를 본다.
3. A가 아니면, 부품 사이 문제의 모양을 고른다: 뜻을 다르게 가정함(B), 전달되지 않음·쓰이지 않음(C), 시점이 어긋남(D).
4. 셋 중 둘에 걸치면 수정이 고친 쪽을 기준으로 하나를 고른다. 걸친 다른 글자는 `also`에 적는다.
5. E와 F는 해당하면 우선한다. 다만 F라도 모델 파일이나 설정이 선언한 템플릿·토크나이저 설정이 무시되거나 덮어써진 경우에는, F로 하고 `flag_declared_overridden: true`를 단다.

## 4. 함께 적을 것

- `letter`: 고른 글자
- `also`: 함께 걸친 글자. 없으면 빈 목록
- `info`: B, C, D일 때 관련된 정보를 쉬운 말로 적는다(예: "양자화 스케일의 형식", "슬라이딩 윈도 크기", "캐시에 쓴 토큰 수").
- `sites`: B, C, D일 때 두 곳을 적는다. "그 정보를 만든 곳 → 그 정보를 쓴 곳" 형식이다.
- `flag_declared_overridden`: true 또는 false
- `confidence`: high, medium, low 가운데 하나
- `reason`: 근거 한두 문장. 근거가 된 URL이나 기록 필드를 적는다.

## 5. 집계 정의 (평정자에게 주지 않는다)

이 절은 결과를 보기 전에 정했다.

- **분모:** 두 평정자가 모두 `eligible: yes`로 판정한 사례
- **좁은 계산:** B + C
- **넓은 계산:** B + C + D, 그리고 `flag_declared_overridden`이 달린 F
- **조용함:** 사례 기록의 `message_at_failure`가 `none`이면 조용한 것으로 센다. 나눠서 낸다.
  - 좁은 계산과 넓은 계산 각각 안에서의 비율
  - 전체에서의 비율
- **일치도:** 코언 카파로 잰다. 세 가지를 따로 낸다.
  - 열 글자 전체
  - 이분(B/C/D 대 나머지)
  - `eligible`
- **불일치:** 한 평정자만 B/C/D로 본 사례는 두 방식으로 모두 센다. 둘 다 그렇게 본 것만 세는 방식(보수), 한쪽이라도 그렇게 본 것을 세는 방식(관대)이다. 결과는 범위로 보고한다.
- **나눠서 낼 것:** LLM 엔진(L 사례)과 이미지 생성(I 사례)을 나눠서 낸다.
- **보충 표본(S 사례, 2026-09-23 추가, S 사례를 보기 전에 적음):** 첫 이미지 표본 50건에서 대상(출력 문제이면서 원인 확인)이 10건뿐이었다. 그래서 수정 PR이 연결된 닫힌 이슈(`linked:pr`)에서 저장소마다 20건까지 더 뽑았다(`collect_image_supplement.py`, 시드 20260925). S는 I와 따로 내고, I+S를 합친 값도 낸다. S는 수정된 이슈 쪽으로 기운 표본이라는 점을 함께 적는다.
- **LLM 표본 확대(2026-09-23 추가, 새 사례를 보기 전에 적음):**
  - 첫 LLM 표본 80건에서 기록자 기준 대상이 25건이라 구간이 너무 넓었다.
  - 그래서 같은 풀의 나머지 303건에서 같은 규칙으로 80건을 더 뽑았다(`make_llm_sample2.py`, 시드 20260925, L081~L160).
  - 같은 모집단에 같은 규칙이므로 첫 표본과 합쳐서 낸다.
- **조용함의 두 번째 분모(2026-09-23 추가, 첫 기록들에서 `unknown`이 많은 것을 보고 더함):** `none`을 전체로 나눈 값에 더해, `none`을 `none`+`warning`+`error`(여부가 알려진 사례)로 나눈 값도 낸다.
- **신뢰 구간:** 비율에는 윌슨 95% 신뢰 구간을 단다.
- **옛 수치와의 비교:** 옛 파일럿(역할 계열 71%, 보수적 59%, 조용함 92%)과의 비교는 참고로만 적는다. 판정 기준으로 쓰지 않는다.
