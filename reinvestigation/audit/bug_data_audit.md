# 실제 버그 기록 파일럿 검증 (2026-09-23)

## 결론

계산 자체는 맞다. 결과 파일에서 머리 수치를 모두 똑같이 다시 얻었다. 역할 계열 50/70(71%), 보수적 40/68(59%), 조용함 46/50, 수치 결함 3건, 카파 0.848과 일치 31/33, 수정 기간 중앙값 13.9일과 12.5일, 증상 26/24다. 무작위 표본 30건도 GitHub에 모두 있다. 근거 문구 30개는 모두 원문에 있고, 조용함 판정은 30건 모두 원문과 맞았다. 엔진 주장 15개도 1차 출처에서 확인됐다. 문제는 수치가 뜻하는 바가 문서의 표현보다 약하다는 점이다. 첫째, 역할 계열 비율은 측정값이라기보다 분류 규칙이 만든 값이다. 같은 자료를 두고 문서가 스스로 89%까지 넓힌 적이 있다. 반대로 경쟁 조건, 한 부품 안의 축 오류, 출시 전 브랜치 결함, 원인 확인이 약한 사례를 빼면 약 55%다. 그러니 "보수적 59%"를 하한으로 볼 수 없다. 둘째, 1차 분류는 가설을 아는 에이전트가 맡았다. 저장소마다 한 명이 검색부터 조용함 판정까지 혼자 했고, 저장소마다 규칙도 달랐다. 블라인드 재분류는 분류 단계만 다시 했다. 코드북은 가설의 틀을 그대로 옮긴 것이었고, 한 건을 평가자 한 명만 봤다. 내세운 카파 0.85는 48건 중 두 쪽이 모두 원인을 정한 33건에서만 잰 값으로, 가장 유리한 수치다(9범주로 재면 0.73). 셋째, 역할 계열 표본 20건 중 5건은 역할 계열 근거로 인정하기 어려웠다. 2건은 분류에 이견이 있고, 3건은 포함 기준에 문제가 있다. 증상 26/24는 조사자가 줄여 쓴 제목에 키워드를 대서 센 것이다. 실제 제목으로 세면 25/25이고, "멀쩡해 보이는 오답"은 깨짐 키워드가 없는 나머지를 모은 범주일 뿐이다. 정리하면 이렇다. 원인이 밝혀진 출력 오류의 다수가 부품 사이 사실 불일치이고 대부분 경고 없이 틀린다는 방향은 자료가 지지한다. 그러나 "약 70%"라는 점 값과 "보수적으로 59%"라는 하한 표현은 고쳐야 한다.

- 방법
  - GitHub은 `gh api -X GET`으로 읽기만 했다. 이슈 본문, 모든 댓글, 타임라인, 연결 PR의 본문과 병합 여부를 읽었고, 필요하면 커밋 diff도 봤다. 댓글, 반응, 작성 같은 쓰기는 하지 않았다.
  - 원자료는 파일로 남기지 않고 메모리에서만 처리했다. 만든 파일은 이 문서와 `bug_data_audit.json` 두 개뿐이다.
- 표본 추출 코드
  - `rng=random.Random(20260924)`
  - `role=[r for r in rows if r['category'].startswith('R')]`
  - `other=[r for r in rows if not r['category'].startswith('R')]`
  - `rng.sample(role,20)`을 먼저 뽑고, 이어서 `rng.sample(other,10)`을 뽑았다. `rows`는 `bug_labels_round1.json`의 순서 그대로다.
- 중간 저장: 20건과 30건을 확인한 뒤 json에 저장했다. 10건째에 해야 할 저장은 빠뜨렸다.

### 1.2 분류 절차 평가

**누가 분류했고, 가설을 알았는가.**
- 1차 분류는 저장소마다 에이전트 한 명이 했다. `bugs_*.md`는 모두 "역할 계열(R1–R4)이 원인인 것은 얼마나 되는가"라는 질문과 정의로 시작한다. 분류한 사람이 가설을 알고 있었다는 뜻이다.
- 같은 에이전트가 검색, 제목 필터, 본문 필터, 표본 선정, 원인 분류, 조용함 판정을 모두 했다. 당시에는 교차 검증이 없었다(`REALWORLD_NOTES.md` 1절의 한계에 적혀 있다).
- 블라인드 재분류의 한계는 다섯 가지다.
  1. 48건(저장소당 12건)을 평가자 두 명이 나눠 봤다. A는 vLLM과 SGLang을, B는 transformers와 llama.cpp를 맡았다. 한 건을 한 명만 봤으므로 비교는 "1차 분류 대 블라인드 1인"뿐이다.
  2. 범주는 중립 문자로 바꿨지만 정의는 역할 분류 체계를 그대로 옮겼다. 예를 들어 F는 "두 부품이 같은 데이터를 다른 규약으로 썼다"이다. 범주 체계 자체를 가설을 아는 쪽이 만들었다.
  3. 평가자에게 준 지시문이 폴더에 남아 있지 않다. 그래서 정말 가설을 몰랐는지 검증할 수 없다.
  4. 다시 한 것은 분류 단계뿐이다. 어떤 이슈를 "출력 오류"로 넣을지 정하는 필터, 표본 선정, N4 규칙은 다시 보지 않았다.
  5. 가장 유리한 부분집합의 카파만 머리 수치로 올렸다(1.1).

**'역할 계열'의 정의는 얼마나 넓은가.**
- R1~R4는 네 가지를 한꺼번에 받는다.
  - 조용히 무시된 모든 설정과 성질
  - 모든 인덱스·오프셋·길이·위치 불일치
  - 모든 배치·순서·dtype·스케일·축 의미 불일치
  - 낡은 상태와 잘못된 시점의 읽기. 동기화 경쟁 조건도 여기에 든다.
- 반면 비역할 범주는 좁다. N1(산술), N2(플랫폼), N3(토크나이저)뿐이다. "보통의 논리 오류", "동시성 버그", "API·설정 설계" 같은 범주가 없어서, 데이터 흐름의 논리 버그는 대부분 역할 계열로 떨어진다.
- `RESEARCH_PLAN.md` 2.1절의 정의는 "두 부품 A와 B 사이"를 요구한다. 그런데 1차 분류는 한 함수 안에서 축을 잘못 고른 경우(transformers #47246, #47475)도 R3로 셌다.
- 가설을 아는 에이전트 한 명이 한 대조군 재검토(`replay_control.md` 5절)는 비역할 20건 중 12건을 역할 계열로 다시 읽었다. `RESEARCH_PLAN.md`의 "최대 약 89%"(62/70)가 여기서 나왔다. 그 문서 스스로 "조용히 무시된 설정을 모두 R1로 세면 정의가 거의 모든 설정 버그를 삼킬 수 있다"고 경고했다. 그런데도 반대 방향, 즉 역할 계열을 비역할로 옮기는 재검토는 하지 않았다.

**규칙 민감도.** 아래 셈의 근거는 두 가지다. 표시한 이슈는 내가 직접 확인했고, 나머지는 문서 자신의 기전 설명을 따랐다.

| 적용한 규칙 | 역할 계열 / 분모 | 비율 |
|---|---|---|
| 문서 기준 | 50/70 | 71.4% |
| A. 경쟁·동기화 6건을 비역할로 (vLLM #42182, #48831, llama.cpp #28537, #23321*, #23717*, #20097) | 44/70 | 62.9% |

- 한쪽 끝은 약 55%, 다른 쪽 끝은 89%다. 그러니 71%는 규칙 하나를 고른 결과다. 어느 규칙을 써도 과반이라는 점은 유지된다.
- 같은 결함을 한 번씩만 세도 비율은 거의 같다. llama.cpp #21589, #21715, #21734는 수정 #21638 하나를 공유하고, vLLM #47087과 #43559는 #51113을 공유한다. 이를 합치면 47/66 = 71.2%다.

### 1.3 표본과 규칙의 일관성

- **표본 시기**
  - 분류한 100건은 "completed로 닫힌 이슈 중 가장 최근 것" 순서로 골랐다. 닫힌 날짜는 vLLM 2026-06-23~09-12, SGLang 07-18~09-20, transformers 02-25~09-21, llama.cpp 04-06~09-10이다.
  - "21개월"은 후보를 모은 기간일 뿐이고 비율의 표본 기간이 아니다.
  - DeepSeek-V4, 하이브리드 모델, 분리 서빙 같은 최신 기능에 몰려 있다. 문서도 이를 한계로 적었다.
- **N4 규칙이 저장소마다 다르다**
  - vLLM은 병합되지 않은 PR에 적힌 기전도 원인으로 셌다(†, #52276, #41472).
  - SGLang은 같은 경우를 N4로 뺐다(#36371, #25882, #30233).
  - transformers는 커밋 이력까지 뒤져 수정을 찾아 원인이 확인된 것으로 셌다(#47246, #47475).
  - SGLang에 vLLM 규칙을 쓰면 비율이 82%에서 74%로 바뀐다(문서의 대안값).
- **포함 기준이 저장소마다 다르다**
  - vLLM은 내부 값만 보고한 이슈(#52924, #46988)와 코드를 읽고 찾은 수식 버그(#41236)를 뺐다. API 계층 문제도 뺐다.
  - transformers는 내부 위치 번호만 보고한 #45381과 코드 읽기 보고인 #45910을 넣었다.
  - llama.cpp는 연산 단위 코드 읽기 보고인 #25027을 넣었다.
  - SGLang은 API 계층 logprob 문제인 #30188을 넣었다.

## 2. 표본 대조

- 역할 계열 20건은 모두 존재했다. 원인 확인 상태는 병합 수정이나 유지보수자 설명으로 확인 18건, 추정 1건, 미확정 1건이다. 조용함 판정은 20건 모두 원문과 맞았다.
  - 판정: 맞음 10, 맞음(단서) 5, 포함 기준 문제 3, 분류 이견 2

## 문제점 목록

중요한 순서로 적는다.

1. **역할 계열 비율은 규칙에 따라 약 55%에서 89%까지 움직인다(1.2).**
   - "약 70%(보수적 59%)"는 이 폭을 감춘다. 59%는 한쪽 방향으로만, 그것도 선택적으로 뺀 값이라 하한이 아니다.
   - 과반이라는 결론은 유지된다. 그러나 점 값을 쓰려면 규칙을 먼저 고정하고 네 저장소에 같이 적용해야 한다.
2. **분류 구조가 가설 쪽으로 기울 수 있었다.**
   - 가설을 아는 에이전트 한 명이 저장소마다 검색부터 조용함 판정까지 모두 했다.
   - 포함 기준과 N4 규칙이 저장소마다 달랐다(1.3).
3. **블라인드 재분류는 신뢰도를 약하게만 보여 준다.**
   - 분류 단계만 다시 했다.
   - 코드북이 가설의 틀을 담고 있다.
   - 한 건을 평가자 한 명만 봤다.
   - 지시문이 남아 있지 않다.
   - 머리의 카파 0.85는 48건 중 33건에서만 잰 가장 유리한 값이다. 9범주는 0.73, 3범주는 0.725다.
4. **표본 20건 중 5건은 역할 계열 근거로 유지되기 어렵다.**
   - 분류 이견: transformers #47246은 수식 오류다. vLLM #41207은 토크나이저 클래스 경계인데, 같은 연구가 transformers의 같은 유형을 N3로 셌다.
   - 포함 기준 문제: transformers #45381은 출력 증상이 없다. SGLang #30176은 출시되지 않은 브랜치의 결함이다. transformers #47752는 설정 우선순위 문제다.
5. **"원인이 확인된 70건"이라는 이름이 부정확하다.** 원인 판단 불가(N5) 2건이 들어 있다. 역할 계열 50건 중 5건은 원인이 추정이거나 미병합 PR에만 적혀 있다(†, ‡, 추정).
6. **증상 집계(26/24)의 근거가 약하다.**
   - 조사자가 줄여 쓴 제목에 키워드를 댄 결과다. 실제 제목으로는 25/25다.
   - "멀쩡해 보이는 오답"은 나머지를 모은 범주다. 본문이 gibberish라고 쓴 이슈(vLLM #51063)와 출력 증상이 없는 이슈(#45381, #45910)가 들어 있다.
   - 이 값이 `PUBLIC_SUMMARY.md`에 실렸다.
7. **"조용함"과 "그럴듯함"은 다르다.** 92%는 오류나 경고가 없었다는 뜻이다. 역할 계열의 절반가량은 사람이 곧바로 알아차리는 깨진 출력이었다. 100건 기준 88%에는 버그가 아닌 사례도 섞여 있다.
8. **표본이 최근에 몰려 있다.** 분류한 100건은 가장 최근에 닫힌 이슈다. 대부분 2026년 2~9월이고, vLLM과 SGLang은 2026년 6~9월이다. "21개월"은 후보를 모은 기간일 뿐이다. 같은 결함을 따로 센 중복도 있다(3건 1묶음, 2건 1묶음).
9. **"수정 기간"은 종료까지의 기간이다.** 봇 종료, 종료 뒤 병합, 수정 뒤 한참 지나서의 종료가 섞여 있다. 두 집단에 차이가 없다는 결론은 유지되지만 이름을 고쳐야 한다.
10. **수치 결함 3건은 규칙에 민감하다.** 같은 48건에서 블라인드 평가자는 N1을 4건 붙였고, 1차 분류는 1건 붙였다.
11. **문서의 사실 오류와 출처 오류가 있다.**
    - `bugs_llamacpp.md` #25382 메모: #26423의 철회를 빠뜨렸다.
