# Phase 0, 3주차 노트: 교차 측정, FlexAttention 비교, 배치 불변성의 비용

- 측정일: 2026-09-22
- 장비·스택: RTX 4070 Ti(모니터 출력 겸용, 잡음 있음), torch 2.14.0+cu130, Triton 3.8.0, transformers 5.17.0
- 코드: `week3/`. 측정은 실제 Qwen3-4B 가중치(`~/models/Qwen3-4B`)로 했다.

## 0. 측정 방식에서 발견한 문제와 수정 (가장 먼저 읽을 것)

### 0.1 transformers 5.17은 넘겨준 위치값을 조용히 무시한다

3주차 설계는 "같은 디코드 위치에서 같은 호출을 수백 번 반복해 시간을 잰다"였다. 처음 결과는 이상했다. 서로 다른 세 어텐션 경로가 모두 로짓 규모만큼 달랐고, 같은 경로를 두 번 돌려도 결과가 달랐으며, 호출을 100번 넘게 반복하면 GPU 경계 검사 오류(device-side assert)로 중단됐다.

원인은 `debug_cache_position.py`로 확정했다.
- transformers 5.17의 모델 호출에는 `cache_position` 인자가 더 이상 없다. 넘겨준 값은 `**kwargs`로 조용히 흡수되어 어디에도 쓰이지 않는다. 오류도 경고도 없다.
- 정적 캐시(StaticLayer)는 쓰기 위치를 자체 GPU 텐서 카운터 `cumulative_length`로 정하고, 호출할 때마다 제자리에서 1을 더한다. RoPE 위치도 이 카운터에서 계산한다.
- 따라서 같은 위치를 반복한다고 생각한 호출은 실제로는 매번 한 칸 뒤에 토큰을 덧붙였다. 카운터가 GPU 텐서라서 CUDA Graph 재생 때도 증가한다. 캐시 여유 128칸을 넘자 인덱스가 범위를 벗어나 경계 검사 오류가 났다.

영향 범위:
- **1·2주차 결과는 유효하다.** 그때는 호출마다 위치를 한 칸씩 올리며 Triton 커널의 유효 길이도 함께 올렸고, 모든 호출이 같은 스텝 함수를 거쳤다. 무시된 위치값 대신 내부 카운터가 같은 속도로 움직였으므로 계산한 위치와 유효 길이가 일치했다. 호출 횟수도 캐시 여유보다 적었다.
- **3주차 첫 측정(v1)과 첫 진단(`debug_model_attn.py`) 결과는 폐기한다.** 경로 간 불일치와 재실행 불일치는 모두 호출마다 다른 위치를 계산한 결과였다.
- 이 과정에서 CUDA Graph 트리에 여러 변형을 번갈아 태우는 방식도 버렸다. 오류의 직접 원인은 위치 카운터였지만, 방식마다 그래프를 따로 캡처하는 편이 더 단순하고 안전하다.

수정(v2 + 되감기):
- 매 호출 전에 모든 층의 위치 카운터를 L로 되돌리는 연산을 캡처한 그래프 안에 함께 넣었다(`torch._foreach_zero_` + `_foreach_add_`).
- 방식마다 CUDA Graph를 따로 캡처하고, 각 그래프의 출력을 같은 방식의 eager 결과와 대조한 뒤에만 시간을 잰다.
- 측정 뒤 카운터가 기대값(L+1)에 있는지 확인한다.
- 방식들을 같은 프로세스 안에서 라운드마다 순서를 바꿔 번갈아 재고, 라운드별 쌍 비교 비율로 보고한다.

확인 결과(배치 1, bf16, 실제 가중치): 같은 sdpa 경로를 두 번 돌리면 비트 단위로 같다. Triton·FlexAttention의 eager 결과는 sdpa와 로짓 최대 0.11~0.14 차이(로짓 규모 14.7)로 일치한다. 모든 그래프가 자기 eager 결과와 일치하고, 카운터는 기대값 513에 있었다.

### 0.2 이 사고가 연구에 주는 의미

넘겨준 인자가 역할을 잃었는데 아무도 알려 주지 않았다. 파이썬의 `**kwargs`는 받는 쪽이 쓰지 않는 인자를 조용히 삼킨다. 역할이 표시된 인자를 컴파일러가 검사하는 언어였다면, 동사가 받지 않는 역할의 인자는 컴파일 오류가 됐을 것이다. `ideas/josa_role_semantics.md`의 아이디어에 대한 구체적 사례로 기록한다.

### 0.3 연산 단위 벤치마크의 함정

`batch_invariance_cost.py`의 2부(행렬곱 연산 단위 비교)는 해석에 주의가 필요하다.
- 작은 가중치(5~50 MB)는 같은 가중치를 반복해 읽는 동안 48 MB L2 캐시에 올라가, cuBLAS가 DRAM 한계(504 GB/s)를 넘는 1,000 GB/s 이상으로 찍혔다.
- 제 커널은 크기와 무관하게 46~48 µs로 나와, 파이썬 쪽 실행 비용에 묶여 있었다.
- 캐시에 들어가지 않는 lm_head(778 MB)만 실제 조건에 가깝다. 여기서 제 커널은 cuBLAS의 1.02배, 약 420 GB/s로 거의 같았다.
- 결론은 CUDA Graph로 파이썬 비용을 없앤 모델 전체 측정으로 낸다.

## 1. 배치 불변성: 달성 여부 (실제 가중치, 강제 입력, 64위치 × 4프롬프트)

같은 프롬프트를 혼자(배치 1) 돌린 결과와 배치 4 안에서 돌린 결과를 비교했다.

| 경로 | 비트 동일 | 최대 차이 | 최상위 토큰 일치 |
|---|---|---|---|
| eager 기본(sdpa, cuBLAS, ATen 정규화) | 4개 모두 아니오 | 0.56 | 95.3% |
| eager Triton 어텐션만 | 4개 모두 아니오 | 0.50 | 95.3% |
| **eager 배치 불변(bi)** | **4개 모두 예** | **0** | **100%** |
| 컴파일 기본 | 4개 모두 아니오 | 0.38 | 95.3% |
| **컴파일 배치 불변(bi)** | **4개 모두 예** | **0** | **100%** |

- 배치 불변 경로와 기본 경로의 차이(배치 4)는 최대 0.44, 평균 0.029, 최상위 토큰 일치 97.3%로 bf16 반올림 수준이다.
- 컴파일한 배치 불변 경로와 eager 배치 불변 경로의 차이는 최대 0.41, 평균 0.029다.
- Triton 어텐션만 바꿔서는 불변이 되지 않는다. 행렬곱(cuBLAS가 배치 1에서 GEMV, 배치 4에서 GEMM을 고름)이 주된 원인이기 때문이다.
- 배치 불변을 만든 방법은 세 가지다. 행렬곱의 분할 방식을 배치 크기가 아니라 행렬 모양으로만 정하고, 정규화를 행마다 고정된 방식으로 계산하고, 어텐션을 (행, 헤드)마다 고정 분할로 계산했다(`bi_kernels.py`).

## 2. 어텐션 경로 교차 측정 (v2 + 되감기, 실제 가중치)

`ab_attention_v2.py`. 프롬프트 512, 디코드 위치 512 고정, 방식마다 CUDA Graph를 따로 캡처, 24라운드 × 12스텝을 번갈아 측정. 표는 스텝 시간의 중앙값이고, 괄호는 라운드별 쌍 비교 비율의 중앙값이다. 모든 조합에서 두 방식은 24라운드 전부 sdpa보다 빨랐다.

| 정밀도 | 배치 | sdpa (transformers 기본) | Triton 커널 (손으로 작성) | FlexAttention (의미를 함수로 전달) |
|---|---|---|---|---|
| bf16 | 1 | 21.54 ms | 20.25 ms (×0.937) | 20.39 ms (×0.941) |
| bf16 | 4 | 26.48 ms | 20.71 ms (×0.782) | 20.70 ms (×0.780) |
| bf16 | 8 | 34.92 ms | 21.73 ms (×0.621) | 21.69 ms (×0.620) |
| int4 | 1 | 8.76 ms | 6.77 ms (×0.774) | 6.88 ms (×0.786) |
| int4 | 4 | 13.31 ms | 7.45 ms (×0.558) | 7.48 ms (×0.560) |
| int4 | 8 | 25.11 ms | 10.51 ms (×0.419) | 10.42 ms (×0.415) |

정확성: 세 방식의 eager 결과는 로짓 규모 13~18에서 최대 0.09~0.31 차이로 일치했고, 각 그래프는 자기 eager 결과와 최대 0.375 이내로 일치했다. 같은 sdpa 경로의 재실행은 모든 경우 비트 단위로 같았다. 측정 뒤 위치 카운터는 모두 기대값 513이었다.

읽는 법:
- **배치가 거의 공짜가 됐다.** 의미를 아는 두 경로는 배치 1에서 8로 갈 때 bf16이 20.3에서 21.7 ms, int4가 6.8에서 10.5 ms로 조금만 늘었다. sdpa 경로는 bf16 21.5에서 34.9 ms, int4 8.8에서 25.1 ms로 크게 늘었다. int4 배치 8의 처리량은 초당 약 320토큰에서 약 760토큰으로 2.4배가 됐다.
- **배치 1 이득도 실재한다.** 2주차 말에 잡음 범위 안이라며 철회했던 배치 1 개선은 교차 측정으로 bf16 6%, int4 23%로 확인됐다. int4에서 더 큰 이유는 가중치 읽기가 4분의 1로 줄어 어텐션 경로의 낭비가 스텝에서 차지하는 비중이 커졌기 때문이다.
- **가장 중요한 결과: 범용 컴파일러가 손 커널과 같은 속도를 냈다.** FlexAttention은 제가 짠 커널이 아니다. "유효 길이보다 작은 위치만 본다"는 뜻을 함수로 적고 헤드 공유를 켰을 뿐이고, 커널은 PyTorch 컴파일러가 생성했다. 그런데 모든 조합에서 손으로 짠 Triton 커널과 2% 이내로 같았다. 이득의 원천은 커널을 잘 짜는 기술이 아니라 컴파일러에 의미를 전달하는 것이었다.
- 단서: FlexAttention의 블록 마스크는 측정 위치에 맞춰 한 번만 만들었다. 실제 디코드에서는 위치가 바뀔 때마다 블록 마스크를 갱신하는 비용이 붙는다. 또 이 경로는 사람이 의미를 직접 함수로 적어야 하고, transformers 기본 경로는 이것을 쓰지 않는다.

## 3. 배치 불변성의 속도 비용 (v2 + 되감기, 실제 가중치, bf16)

`bi_speed_v2.py`. default는 sdpa + cuBLAS + Inductor 정규화, tri_attn은 Triton 어텐션만 교체, bi는 Triton 어텐션 + 배치 불변 행렬곱 + 배치 불변 정규화다. 모든 그래프가 자기 eager 결과와 일치했고 카운터는 513이었다.

| 배치 | default | tri_attn | bi (배치 불변) | bi 대 tri_attn = 불변성의 가격 |
|---|---|---|---|---|
| 1 | 23.27 ms | 22.00 ms (×0.947) | 22.73 ms (×0.978) | +3.3% |
| 4 | 29.78 ms | 23.69 ms (×0.791) | 23.60 ms (×0.789) | −0.4% |
| 8 | 39.21 ms | 24.60 ms (×0.628) | 24.74 ms (×0.630) | +0.6% |

- 배치와 무관하게 같은 답을 보장하는 비용은 배치 1에서 약 3%, 배치 4·8에서 사실상 0이었다. Thinking Machines가 보고한 34~110% 감속과 크게 다르다. 가중치 읽기가 지배하는 소비자 GPU 디코드에서는 행렬곱 분할을 배치와 무관하게 고정해도 잃는 것이 거의 없다.
- 배치 불변 경로는 모든 배치에서 기본 경로보다 빨랐다(2%, 21%, 37%). 어텐션 경로 개선이 불변성 비용을 덮고도 남는다.
- 이 측정은 모니터를 내장 그래픽으로 옮긴 직후에 돌았고 흔들림이 컸다(4절). 비율은 라운드 쌍 비교라 유지되지만, 절대 시간은 2절 표보다 3~12% 높게 나왔다.

## 4. 모니터를 내장 그래픽으로 옮긴 뒤의 GPU 상태 (19:47)

- 4070 Ti의 화면 출력은 꺼졌다(display_active Disabled). NVIDIA Overlay, 검색, 입력기 프로세스는 이 카드에서 빠졌다.
- 그러나 탐색기, ApplicationFrameHost, 카카오톡, Claude 데스크톱 앱, Edge WebView2는 여전히 4070 Ti에 그래픽 컨텍스트를 잡고 있다. 대기 상태 사용률 35~42%, VRAM 약 500 MiB이고, 클럭 상태는 오히려 P8(210 MHz)에서 P5(660~705 MHz)로 올라갔다. 이 앱들이 4070 Ti에서 그린 화면을 내장 그래픽으로 복사하는 것으로 보인다.
- 흔들림은 오히려 커졌다(`noise_check.py`, 3초 예열 후 300회).

| 작업 | 모니터 4070 Ti | 모니터 내장 그래픽, 앱은 4070 Ti |
|---|---|---|
| 행렬곱 4096 | 변동계수 12%, p95 1.31배 | 변동계수 27%, p95 1.83배 |
| 256 MiB 복사 | 변동계수 18%, p95 1.51배 | 변동계수 35%, p95 2.28배 |
| 작은 커널 200개 | 변동계수 15%, p95 1.33배 | 변동계수 31%, p95 1.77배 |

- 조치: 재부팅하면 셸과 앱이 화면을 담당하는 내장 그래픽에서 새로 시작할 가능성이 높다. 재부팅 뒤 `nvidia-smi`의 프로세스 목록과 `noise_check.py --tag display_on_igpu_after_reboot`로 다시 확인한다. 그래도 앱이 4070 Ti에 남으면 Windows 설정의 시스템 → 디스플레이 → 그래픽에서 해당 앱의 GPU 기본 설정을 절전으로 바꾼다.

### 4.1 재부팅 뒤 (2026-09-22)

재부팅하자 모든 앱과 셸이 화면을 담당하는 내장 그래픽에서 시작했다. 4070 Ti는 대기 상태에서 사용률 0%, VRAM 0 MiB, P8, 7.2 W이고 이 카드를 쓰는 프로세스가 하나도 없다. Nsight Compute 카운터 권한도 유지됐다.

| 작업 | 모니터 4070 Ti | 내장 그래픽, 앱은 4070 Ti | **내장 그래픽, 재부팅 뒤** |
|---|---|---|---|
| 행렬곱 4096, 변동계수 | 12.3% | 27.4% | **0.9%** |
| 256 MiB 복사, 변동계수 | 18.5% | 35.3% | **0.9%** |
| 작은 커널 200개, 변동계수 | 14.8% | 30.6% | 21.6% |
| 지속 행렬곱 처리량 | 71.6 TFLOPS | 66.5 TFLOPS | **79.1 TFLOPS** |

- GPU가 주도하는 작업의 흔들림은 1% 아래로 사라졌다. 지속 처리량은 GeForce FP32 누산 상한 약 80 TFLOPS에 도달했다. 화면과 앱이 이 카드 처리량의 약 10%를 가져가고 있었다는 뜻이다.
- 작은 커널을 파이썬에서 연속 실행하는 작업은 여전히 흔들린다. 이것은 GPU가 아니라 WSL 가상 머신의 CPU 스케줄링에서 오는 흔들림이다. CPU가 병목인 eager 측정에서는 계속 교차 측정을 쓰고, 가능하면 CUDA Graph로 파이썬 실행을 측정 밖으로 뺀다.
- WSL 안에서 보이는 "다른 프로세스 점유 1.22 GiB"는 세 조건에서 같았다. 이 값은 우리 프로세스의 CUDA 컨텍스트와 WSL 쪽 예약분이지 다른 앱의 사용량이 아니다. `noise_check.py`의 해당 출력 이름은 오해를 부르므로 해석할 때 주의한다.
- 1~3주차의 절대 시간은 약 10% 처리량을 잃고 흔들리는 상태에서 잰 것이다. 교차 측정으로 얻은 비율은 유효하지만, 절대 시간은 지금 다시 재면 더 빨리 나온다. 논문용 기준 수치는 이 조건에서 다시 잰다.

## 5. 3주차 요약

1. transformers 5.17은 위치 인자를 조용히 무시한다. 3주차 첫 측정은 폐기했고, 위치 카운터를 되감는 방식으로 다시 쟀다. 1·2주차 결과는 유효하다.
2. 컴파일러에 의미(유효 길이, 헤드 공유)를 전달하는 두 경로는 배치 1~8에서 transformers 기본 경로보다 bf16 6~38%, int4 23~58% 빨랐다. int4 배치 8 처리량은 2.4배다.
3. 의미를 함수로 적어 준 FlexAttention이 손으로 짠 커널과 모든 조합에서 2% 이내로 같았다. 이득의 원천은 커널 작성 기술이 아니라 의미 전달이다.
4. 배치 불변성은 eager와 컴파일 모두에서 비트 단위로 달성했고, 속도 비용은 0~3%였다.
5. 모니터를 옮긴 직후에는 앱이 4070 Ti에 남아 오히려 흔들렸지만, 재부팅 뒤 4070 Ti는 완전히 비었다. GPU 작업의 흔들림은 1% 아래가 됐고 지속 처리량은 약 10% 올랐다.
