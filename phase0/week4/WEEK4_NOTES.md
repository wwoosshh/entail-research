# Phase 0, 4주차 노트: 기존 컴파일러는 의미를 찾느라 헛수고를 하는가

- 측정일: 2026-09-22. 재부팅 뒤라 4070 Ti는 화면 출력 없이 계산만 한다(3주차 노트 4.1절).
- 장비·스택: RTX 4070 Ti 12 GB, torch 2.14.0+cu130, Triton 3.8.0, transformers 5.17.0, 실제 Qwen3-4B 가중치.
- 코드: `week4/`. 결과 JSON은 `week4/results/`, 로그는 `week4/logs/`.

## 0. 질문과 판정 규칙

사용자의 질문은 두 단계다.
1. 기존 컴파일러가 실제로 의미를 비효율적으로 찾고 있는가. 의미가 명확히 전달되지 않아 추론의 성능이나 안정성에 손실이 생기는가. 이것을 데이터로 확인한다.
2. 조사로 역할을 선언하는 컴파일러가 그 손실을 없애는가. 만약 1에서 탐색이 그렇게 비효율적이지 않다고 판정되면, "더 빨리, 더 확실하게 찾는다"는 주장만으로는 부족하므로 다른 이점을 찾는다.

손실을 다섯 종류로 나눠 따로 쟀다. 앞의 두 개가 "찾는 수고", 뒤의 세 개가 "전달의 실패"다.

| 손실 | 뜻 | 실험 |
|---|---|---|
| 컴파일 중 탐색 | 컴파일러가 파이썬 코드에서 프로그램의 의미를 복원하는 시간 | E1 |
| 실행 중 탐색 | 매 호출 가정을 다시 검사하거나, 지워진 구조를 매 스텝 다시 찾아내는 비용 | E1, E3, E3b |
| 추측 실패 | 관측한 값으로 특화했다가 틀려서 다시 컴파일하는 비용 | E1, E2 |
| 의미 소거 | 전달 과정에서 사실이 지워져 빠른 경로를 쓰지 못하는 손실 | E4 |
| 조용한 오류 | 역할이 모호하거나 사실이 엉뚱한 때에 읽혀 틀린 답이 경고 없이 나오는 손실 | E5, hf_flex 진단 |

선언하는 쪽의 해법은 `rolec.py`(역할 타입 프런트엔드 시제품)와 각 실험의 "선언" 변형으로 보였다.

## 1. 판정 요약

**기존 컴파일러의 "찾는 수고"는 크지 않다. 손실은 찾기 전에 생긴다.** 사실이 인터페이스에서 지워지거나, 추측으로 대신되거나, 엉뚱한 때에 읽힌다. 지워진 사실은 더 잘 찾아도 돌아오지 않는다. 그래서 "의미를 더 빨리 찾는 컴파일러"는 이점이 되지 못하고, "의미가 지워지지 않고 잘못 전달될 수 없는 컴파일러"가 이점이 된다.

| 손실 | 측정 결과 | 선언했을 때 |
|---|---|---|
| 컴파일 중 탐색 | 콜드 컴파일 40.1 s 중 약 8 s(20%), 한 번만 | 코드 생성 80%는 그대로 남는다 |
| 실행 중 가드 검사 | 가정 6,432개, 호출 시간 차이 없음 | 해당 없음 |
| 실행 중 재발견 (디코드) | 그래프 안에서 스텝의 0.2~1.5%. 호스트에서 부르면 +48~61% | 12 µs, 더 강한 사실 |
| 실행 중 재발견 (긴 문맥) | 128K에서 60 ms, 한 층 어텐션의 1.7배, N²로 증가 | 약 1.8 ms로 일정 |
| 추측 실패 | 새 배치의 첫 요청이 66~106 s 멈춤. 선언 하나는 조용히 무시됨 | 미리 컴파일하면 0, 또는 한 번만 |
| 의미 소거 | 기본 경로가 1.3~2.5배 느림 | 컴파일 시점 상한과 2% 안 |
| 조용한 오류 | 역할 실수 8종 모두 무증상. 라이브러리 자체 결함 1건 새로 확인했으나 보통 사용에서는 잠복 | 8종 모두 거부, 표현 불가, 규칙으로 제거 |

## 2. E1: torch.compile 해부 (컴파일 중 탐색, 가드, 재컴파일)

`e1_compile_anatomy.py`. Qwen3-4B 디코드 한 스텝(bf16, sdpa, 배치 1)을 캐시를 비운 상태에서 컴파일했다. 단계별 시간은 PyTorch 내부 계측(`compilation_time_metrics`)에서 읽었다.

| 항목 | 값 |
|---|---|
| 콜드 컴파일 전체 | 40.1 s |
| Dynamo: 파이썬 바이트코드를 따라가며 연산 그래프를 복원 | 약 4.2 s |
| AOT: 함수화, 메타데이터 수집 | 약 3.7 s |
| Inductor: 융합 결정, 하향, 코드 생성, Triton 컴파일 | 약 30.9 s |
| 그중 융합 결정(Scheduler) | 12.9 s |
| 매 호출 검사하는 가정(가드) | 6,432개 |
| 가드를 검사할 때와 건너뛸 때의 호출 시간 | 22.42 ms / 22.75 ms |
| 배치 1에서 4로 바뀔 때 재컴파일 | 61.5 s |

- 재컴파일 이유는 로그에 이렇게 남았다: `tensor 'c.layers[0].keys' size mismatch at index 0. expected 1, actual 4`. 처음 본 배치 1을 고정된 사실로 추측했다가 틀린 것이다.
- 가드 종류 상위는 차원 동적 표시 2,540개, 타입 일치 1,237개, 딕셔너리 키 833개, 텐서 일치 508개였다.

읽는 법:
- 의미를 복원하는 데 드는 시간(Dynamo와 AOT)은 약 8 s로 컴파일의 약 20%다. 나머지 약 80%는 코드 생성으로, 의미를 처음부터 알고 있어도 해야 하는 일이다.
- 두 단계가 찾는 것은 역할 정보다. Dynamo는 파이썬 객체의 타입과 모양을 관측해 가정으로 고정한다. AOT는 가짜 텐서로 그래프를 한 번 돌려 어떤 입력이 변경되고 어떤 입력이 읽히기만 하는지, 출력이 입력과 메모리를 공유하는지를 알아낸다. 뒤의 것은 조사 "에"(쓰기 대상)와 "에서"(읽기 전용 출처)가 선언하려던 정보와 같다.
- 실행 중 가드 검사 비용은 측정 잡음 안이다. 6,432개의 가정을 매번 다시 확인해도 호출당 비용은 보이지 않았다.
- 가장 큰 비용은 추측이 틀렸을 때다. 재컴파일 61.5 s는 콜드 컴파일 40.1 s보다 길다. 동적 shape로 다시 추적하면서 그래프 복원과 코드 생성을 모두 다시 하기 때문이다.

## 3. E2: 배치 크기를 추측할 것인가, 선언할 것인가

`e2_shape_guessing.py`. 디코드 서버에 배치 1, 4, 8, 2가 이 순서로 들어온다고 보고, 방식마다 새 프로세스에서 캐시를 비운 채 시작했다. 첫 스텝 시간에는 그때 일어난 컴파일이 들어 있다. 정상 상태는 16스텝 중 5번째부터의 중앙값이다. CUDA Graph 없이 torch.compile 기본 모드로 쟀으므로 절대 시간은 E3, E4보다 크다.

| 방식 | 서비스 전 준비 | 서비스 중 멈춤 | 그래프 수 | 정상 상태 B1 / B4 / B8 / B2 (ms) |
|---|---|---|---|---|
| 자동 추측 (기본값) | 0 | 111 s (B1 45.1 s, B4 66.3 s) | 2 | 21.8 / 30.0 / 36.1 / 28.1 |
| 모든 차원 동적 (`dynamic=True`) | 0 | 171 s (B1 65.5 s, B4 105.6 s) | 2 | 22.4 / 30.4 / 36.6 / 28.1 |
| 배치 차원에 동적 표시 (`mark_dynamic`) | 0 | 116 s (B1 46.8 s, B4 69.2 s) | 2 | 23.5 / 29.9 / 35.9 / 25.7 |
| 배치를 값 모르는 크기로 선언 (`mark_unbacked`) | 0 | 70.3 s (B1만) | 1 | 22.7 / 30.4 / 36.5 / 28.5 |
| 배치 크기 집합을 선언하고 미리 컴파일 | 199.8 s | 0 | 4 | 21.7 / 29.9 / 36.1 / 27.7 |
| 값 모르는 크기 + 같은 배치라는 관계 선언 (`shape_id`) | 0 | 66.9 s (B1만) | 1 | 24.0 / 30.4 / 36.5 / 27.6 |

읽는 법:
- 추측에 기대는 세 방식은 모두 배치 4가 처음 들어올 때 66~106초 멈췄다. 처음 본 배치 1을 고정된 사실로 추측했다가 틀렸기 때문이다. 서버라면 그 요청과 뒤에 줄 선 요청이 1~2분을 기다린다.
- `mark_dynamic`은 배치 1에서 "이 차원은 변한다"고 표시했는데도 배치 4에서 다시 컴파일했다. 크기 0과 1은 항상 상수로 특화한다는 내부 규칙 때문으로 보인다. 같은 조건에서 "값 모르는 크기"로 선언한 방식은 다시 컴파일하지 않았다. 기본 로그 수준에서는 경고가 없었다. 선언이 조용히 무시된 것이고, E5에서 조용히 삼켜진 `sliding_window`와 같은 종류의 문제다.
- 배치를 "값을 모르는 크기"로 선언하자 한 번의 컴파일로 네 배치를 모두 처리했다. 정상 상태 속도는 배치별로 따로 컴파일한 그래프보다 배치 1에서 4~10% 느렸고, 나머지 배치에서는 0~3% 차이였다.
- 73개 텐서가 같은 배치라는 관계(`shape_id`)를 함께 선언해도 결과는 같았다. 관계를 선언하지 않았을 때도 컴파일러가 실행 중 검사를 넣어 처리했다. 이 모델에서는 관계 선언이 필요하지 않았다.
- 이 선언은 PyTorch 2.14 릴리스 글이 말하는 선언형 동적 shape(`@dynamic_spec`)의 바탕 기능이다. 설치된 2.14.0에서는 그 이름의 API를 찾지 못해 `mark_unbacked`로 직접 선언했다.
- 배치 크기 집합을 선언하면 컴파일이 모두 서비스 전으로 옮겨져 서비스 중 멈춤이 없다. 서빙 엔진이 시작할 때 배치 크기 목록으로 CUDA Graph를 미리 캡처하는 관행과 같다.
- 정리: 추측이 틀리면 1~2분이 사라지고, 선언하면 이 비용이 없어진다. 다만 지금의 선언 수단은 설정 플래그와 개별 API로 흩어져 있고, 그중 하나는 조용히 무시됐다.

## 4. E3: 실행 중 재발견 (디코드, 위치가 매 스텝 전진)

`e3_rediscovery.py`. int4 Qwen3-4B, 프롬프트 512, 한 라운드에 48스텝 동안 디코드 위치가 전진한다. 방식마다 CUDA Graph를 따로 캡처하고 8라운드를 번갈아 쟀다. 스텝 p에서 필요한 사실은 "키 0부터 p까지가 유효하다"이다. FlexAttention 네 변형은 같은 컴파일된 어텐션 커널을 쓰고, 그 스텝의 블록 정보를 얻는 방법만 다르다.

| 방식 | 사실을 얻는 방법 | 배치 1 | 배치 8 |
|---|---|---|---|
| sdpa (transformers 기본) | 매 스텝 참/거짓 마스크를 새로 만들어 넘긴다 | 9.14 ms | 23.19 ms |
| 손 커널 (Triton) | 유효 길이를 직접 읽는다 | 6.98 ms | 9.38 ms |
| Flex, 선언 산술 | "까지 p"에서 블록 수를 산술로 계산한다 | 7.09 ms | 9.17 ms |
| Flex, 전문가 요령 | 미리 만든 인과 블록 마스크에서 한 행을 고른다 | 7.09 ms | 9.10 ms |
| Flex, 그래프 안 재발견 | 매 스텝 마스크 함수를 모든 키 위치에 평가해 블록을 다시 찾는다 | 캡처 실패 | 9.19 ms |
| Flex, 그래프 안 재발견, 컴파일 | 같은 일을 문서 권고대로 컴파일해서 한다 (추가 실행) | 7.11 ms | 9.31 ms |
| Flex, 호스트 재발견 | 같은 일을 그래프 밖 호스트에서 매 스텝 한다 | 11.24 ms | 13.67 ms |
| transformers 내장 Flex | 라이브러리가 그래프 안에서 블록 마스크를 다시 만든다 | 7.11 ms, 답이 틀림 | 답이 틀려 제외 |

추가 실행(`results/e3_rediscovery_extra.json`)에서 같은 프로세스 안의 선언 산술은 배치 1에서 7.07 ms, 배치 8에서 9.24 ms였다. 호스트 재발견은 11.37 ms와 13.66 ms로 첫 실행과 같은 결과였다.

블록 정보를 얻는 일만 따로 잰 비용:

| 방법 | GPU 시간 (그래프 안) | 호스트에서 한 번 부를 때 |
|---|---|---|
| 선언 산술 | 12~14 µs | 0.20 ms |
| 전문가 요령 | 12 µs | 0.17~0.18 ms |
| 재발견, 컴파일 | 31 µs | 1.0 ms |
| 재발견, eager (create_block_mask) | 80~86 µs | 3.1~3.7 ms |

재발견은 더 약한 사실을 얻는다(`diag_block_meta.py`). 위치 512에서 선언 산술은 "블록 0~3은 전부 유효, 블록 4만 일부 유효"를 안다. `create_block_mask`는 다섯 블록 모두를 "일부 유효"로 분류했다. 질의 한 줄을 128줄 블록으로 채운 격자에서 판정 함수를 평가하므로, 채운 줄 때문에 어느 블록도 "전부 유효"라고 증명하지 못한다. 그 결과 커널은 선언 쪽보다 네 블록에서 더 마스크 함수를 계산한다. 두 경로의 출력이 비트 단위로 다른 것도 이 때문이다. 둘 다 sdpa와는 bf16 잡음 수준으로 일치했다.

정확성: 위치가 전진하는 6스텝 동안 sdpa와 비교해 손 커널, 선언 산술, 전문가 요령, 재발견 변형은 두 번의 실행에서 모두 로짓 최대 차이 0.19~0.34, 최상위 토큰 일치 96~100%였다(로짓 규모 19.6~24.5). 100%가 아닌 경우는 선언 산술과 재발견에서 똑같이 나왔고, 1, 2위 토큰 점수가 거의 같은 자리의 bf16 차이다. transformers 내장 Flex는 최대 차이 2.8(배치 1)과 11.1(배치 8), 최상위 토큰 일치 67%와 71%였다. 원인은 7절에서 진단한다.

읽는 법:
- 재발견은 선언보다 GPU 일을 3~7배 더 한다. 그래도 절대량은 스텝의 1% 미만이다. 그래프 안에 넣으면 선언보다 0.2~1.5% 느린 정도다.
- 같은 일을 호스트에서 매 스텝 부르면 스텝이 48~61% 느려진다. 배치 1에서는 sdpa보다도 23~24% 느려져, 의미를 아는 경로로 얻은 이득을 전부 잃는다.
- 배치 1의 eager 재발견을 모델과 함께 그래프에 캡처하는 것은 두 번의 실행 모두 실패했다. 같은 함수만 따로 캡처하면 성공했고 배치 8에서도 성공했다. 원인은 특정하지 못했다. 컴파일한 재발견은 두 배치 모두에서 캡처됐다.
- 결론: 실행 중 탐색 비용은 전문가가 재발견을 컴파일해 그래프 안에 넣으면 작고, 자연스러운 방식으로 쓰면 크다. 선언 방식은 배치에 신경 쓰지 않아도 항상 작고, 더 강한 사실을 준다.

## 5. E3b: 길이가 늘 때 재발견 비용 (여러 문서를 이어 붙인 인과 마스크)

`e3b_mask_scaling.py`. 문서 경계와 인과성으로 정해지는 마스크는 배치마다 바뀌므로 FlexAttention에서 블록 마스크를 매번 새로 만들어야 하는 대표 사례다. 프로그래머는 구조(문서 경계, 인과)를 알지만 API는 원소 단위 판정 함수만 받는다. 그래서 `create_block_mask`는 N×N 모든 위치에서 함수를 평가해 128×128 블록 중 어느 것이 비었고, 일부만 차고, 가득 찼는지 다시 찾아낸다. 선언 방식은 블록 단위 문서 범위로 같은 정보를 계산한다. 두 방식의 블록 구조는 모든 길이에서 같았고, FlexAttention 출력은 비트 단위로 같았다.

첫 실행(`results/e3b_mask_scaling.json`, 2K~32K):

| 길이 N | 문서 수 | 비어 있지 않은 블록 / 하삼각 블록 | 재발견, eager | 재발견, 컴파일 | 선언, eager | 어텐션 1층 순전파 |
|---|---|---|---|---|---|---|
| 2,048 | 2 | 136 / 136 | 4.40 ms | 1.00 ms | 1.47 ms | 0.72 ms |
| 4,096 | 4 | 293 / 528 | 4.61 ms | 1.02 ms | 1.35 ms | 1.42 ms |
| 8,192 | 8 | 450 / 2,080 | 7.23 ms | 0.97 ms | 1.51 ms | 4.44 ms |
| 16,384 | 16 | 1,027 / 8,256 | 21.95 ms | 3.12 ms | 1.46 ms | 4.68 ms |
| 32,768 | 32 | 2,670 / 32,896 | 측정 안 함 | 5.03 ms | 1.42 ms | 11.07 ms |

보강 실행(`results/e3b_mask_scaling_v2.json`, 선언 쪽도 컴파일, 128K까지):

| 길이 N | 재발견, 컴파일 | 선언, 컴파일 | BlockMask 생성만 | 어텐션 1층 순전파 | 재발견 / 36층 어텐션 | 선언 / 36층 어텐션 |

| 4,096 | 0.90 ms | 1.62 ms | 1.10 ms | 1.39 ms | 1.8% | 3.2% |

| 32,768 | 4.38 ms | 1.26 ms | 0.92 ms | 11.07 ms | 1.1% | 0.3% |
| 65,536 | 14.79 ms | 1.37 ms | 0.98 ms | 19.18 ms | 2.1% | 0.2% |

읽는 법:
- 재발견 비용은 N의 제곱으로 늘고, 선언 방식은 길이와 무관하게 거의 일정하다. 32K에서 재발견은 블록 2,670개를 찾으려고 판정 함수를 약 10억 번 평가한다. 128K에서는 약 170억 번이고, 한 층 어텐션 순전파의 1.7배가 걸린다.
- 선언 방식의 시간은 대부분 BlockMask 객체를 만드는 고정 비용(약 1 ms)이다. 선언 자체의 계산은 0.3~0.6 ms다. 짧은 길이에서는 이 고정 비용 때문에 선언이 컴파일된 재발견보다 느리다.
- 블록 마스크는 한 번 만들어 모든 층이 함께 쓴다. 36층 어텐션과 비교하면 재발견은 32K까지 1~2%, 128K에서 4.9%다. 문서 길이가 일정하면 어텐션 일은 N에 비례하고 재발견은 N의 제곱에 비례하므로, 길이가 늘수록 비중이 커진다.
- 결론: 이 범위에서 재발견은 큰 손실이 아니다. 다만 비용이 구조적으로 더 빨리 자라고, 매우 긴 문맥에서는 어텐션 자체를 넘어선다.

## 6. E4: 사실을 하나씩 빼 보기 (의미 소거의 크기)

`e4_fact_ablation.py`. 3주차 v2 방식(실제 가중치, 디코드 위치 512 고정, 방식마다 CUDA Graph, eager 대조, 20라운드 × 10스텝 교차 측정)으로, 어텐션 호출에 넘기는 사실의 조합만 바꿨다.
- 사실 없음: transformers 기본. 유효 범위는 참/거짓 마스크로, 헤드 공유는 KV 복사(repeat_kv)로 풀려 있다.
- 공유만: 같은 마스크를 쓰되 헤드 공유를 SDPA의 `enable_gqa`로 알려 준다.
- 둘 다, 범용 컴파일러: FlexAttention에 유효 길이를 함수로, 공유를 `enable_gqa`로 준다. 커널은 Inductor가 만든다.
- 둘 다, 손 커널: 2주차 Triton 커널.
- 상한: 유효 길이를 컴파일 시점 상수로 고정해 캐시를 잘라 넘기고 flash 커널을 쓴다. 위치가 고정된 이 측정에서만 가능한 참고값이다.

모든 그래프는 자기 eager 결과와 일치했고, 위치 카운터는 기대값 513이었다.

| 설정 | 사실 없음 | 공유만 | 둘 다, 범용 컴파일러 | 둘 다, 손 커널 | 상한 |
|---|---|---|---|---|---|
| bf16 배치 8 | 36.18 ms | 26.52 ms (×0.734) | 22.53 ms (×0.623) | 22.49 ms (×0.622) | 22.29 ms (×0.617) |
| int4 배치 1 | 9.28 ms | 8.07 ms (×0.868) | 7.14 ms (×0.769) | 7.04 ms (×0.757) | 7.16 ms (×0.769) |
| int4 배치 4 | 13.97 ms | 10.52 ms (×0.752) | 7.94 ms (×0.569) | 7.99 ms (×0.574) | 7.97 ms (×0.571) |
| int4 배치 8 | 23.03 ms | 13.36 ms (×0.580) | 9.25 ms (×0.402) | 9.39 ms (×0.407) | 9.07 ms (×0.394) |

모든 비교에서 20라운드 전부 사실 없음보다 빨랐다.

한 스텝의 GPU 커널 시간 분해 (int4 배치 8, ms):

| 방식 | 어텐션 | KV 복사와 마스크 준비 | 행렬곱 | 합계 |
|---|---|---|---|---|
| 사실 없음 | 8.68 | 6.50 | 7.03 | 22.64 |
| 공유만 | 5.86 | 0.12 | 6.62 | 13.00 |
| 둘 다, 범용 컴파일러 | 1.89 | 0.09 | 6.59 | 8.91 |
| 둘 다, 손 커널 | 1.84 | 0.10 | 6.77 | 9.05 |
| 상한 | 1.72 | 0.05 | 6.64 | 8.74 |

읽는 법:
- **어느 사실이 얼마를 설명하나.** 전체 이득 가운데 헤드 공유가 57~71%, 유효 길이가 29~43%를 설명한다. 공유를 모르면 매 스텝 KV를 헤드 수만큼 복사한다. bf16 배치 8에서 이 복사는 약 3 GB의 쓰기로, 측정된 6.2 ms와 규모가 맞는다. 유효 길이를 모르면 마스크를 읽는 범용 커널을 써야 해서, 어텐션 자체가 5.9 ms에서 1.9 ms로 줄 기회를 잃는다.
- **사실을 받은 범용 컴파일러는 상한과 같다.** FlexAttention은 손 커널과 1.5% 안, 컴파일 시점 상수를 쓴 상한과 2% 안이었다. 사실이 전달되기만 하면 코드 생성은 문제가 아니었다.
- **같은 사실도 어느 층이 받느냐에 따라 버려진다.** 공유만 알려 준 경로는 eager에서 기본 경로와 비트 단위로 같았다. SDPA가 내부에서 결국 복사를 하기 때문으로 보인다. 컴파일된 그래프에서는 Inductor가 이 사실을 써서 복사를 없앴다.
- 사실 없음 경로에서는 같은 행렬곱 커널도 공유만 경로보다 2~28% 느렸다. 복사 트래픽이 이웃 커널까지 늦추는 것으로 보이지만 원인은 따로 분리하지 않았다.
- 3주차 표(재부팅 전, 화면 출력 겸용)와 비율이 거의 같다. 예를 들어 int4 배치 8의 손 커널 비율은 3주차 ×0.419, 이번 ×0.407이다.
- 이 손실은 컴파일러가 더 잘 찾는다고 줄지 않는다. 마스크를 받은 시점에 "앞에서부터 연속된 구간"이라는 사실은 이미 없다. 참/거짓 표를 훑어 이 사실을 되찾는 것은 가능하지만, 그 자체가 E3의 재발견 비용이고 값에 따라 달라지는 검사라 그래프에 고정할 수도 없다.

## 7. 조용한 오류: E5 역할 오류 주입과 transformers 내장 Flex 진단

### 7.1 E5: 역할 오류 8종 주입

`e5_role_errors.py`. 어텐션에서 실제로 흔한 역할 실수 8가지를 기존 파이썬 인터페이스와 rolec에 똑같이 넣었다.

| 실수 | 기존 스택 | 올바른 결과와의 차이 (상대) | rolec |
|---|---|---|---|
| 키와 값을 바꿔 넘김 | 조용히 실행 | 152% | 실행 전 거부 |
| GQA 헤드 확장을 repeat로 (repeat_interleave가 맞음) | 조용히 실행 | 139% | 표현 불가 (공유는 Share로 선언, 헤드 대응은 프런트엔드가 한다) |
| 마스크 참/거짓 뜻을 반대로 | 조용히 실행 | 176% | 표현 불가 (마스크 인자가 없다) |
| 참/거짓 마스크를 덧셈 마스크로 | 조용히 실행 | 65% | 표현 불가 |
| 유효 범위를 한 칸 덜 (배타 대 포함) | 조용히 실행 | 24% | 언어 규칙으로 제거 (까지는 포함) |
| transformers sdpa 경로에 넘긴 sliding_window가 무시됨 | 조용히 실행 | 82% | 실행 전 거부 (받지 않는 역할) |
| [B,L,H,D]를 [B,H,L,D]로 읽음 (L과 H가 같을 때) | 조용히 실행 | 112% | 이름 붙은 차원으로 올바르게 실행 |
| 질의가 키보다 적을 때 is_causal 정렬 | 조용히 실행 | 385% | 선언한 절대 위치로 올바르게 실행 |

- 기존 스택은 8개 모두 오류도 NaN도 없이 틀린 답을 냈다. rolec은 2개를 실행 전에 거부했고, 3개는 표현 자체가 불가능했고, 1개는 언어 규칙으로 사라졌고, 2개는 모호한 형태가 없어서 올바르게 실행됐다.
- 올바른 호출끼리는 두 인터페이스 모두 기준값과 0.2% 이내로 일치했다.

### 7.2 transformers 내장 Flex 경로의 한 칸 초과 (실제 라이브러리 결함)

E3에서 transformers 내장 FlexAttention 경로만 답이 틀렸다. 위치가 전진하는 6스텝에서 최상위 토큰이 배치 1에서 33%, 배치 8에서 29% 바뀌었다. 원인을 소스에서 찾고 eager 모드에서 확인했다(`diag_hf_flex_offset.py`).

원인:
- transformers 5.17의 마스크 생성은 질의의 위치를 정적 캐시의 카운터 텐서 자체로 받는다. `get_query_offset`이 `cumulative_length`를 그대로 돌려준다. 값이 아니라 참조다.
- FlexAttention용 마스크 함수는 이 텐서를 붙잡아 두었다가 커널이 실행될 때 읽는다.
- 그런데 각 층의 캐시 갱신이 어텐션 직전에 카운터를 제자리에서 1 올린다. 그래서 커널이 읽는 위치는 p가 아니라 p+1이고, 이번 스텝에 쓰지 않은 칸 p+1까지 본다.
- sdpa 경로는 마스크를 만드는 순간 참/거짓 표로 굳혀 두므로 영향이 없다.

확인 결과(eager, 컴파일과 CUDA Graph 없음, bf16, 배치 1, 위치 512, 로짓 규모 14):

| 경우 | 내장 Flex 대 sdpa | 내장 Flex 대 "키 p+1까지 읽는 손 커널" |
|---|---|---|
| p+1 칸이 비어 있음 (새 캐시) | 최대 0.06 | 최대 0.08 |
| p+1 칸에 이전 데이터가 남아 있음 | 최대 0.81 | 최대 0.07 |
| 이전 데이터가 있고, 위치를 생성 시점의 값으로 복사해 넘김 | 최대 0.09 | 최대 0.75 |

- 이전 데이터가 있을 때 내장 Flex는 "키 p+1까지 읽는 커널"과 잡음 수준으로 같다. 한 칸을 더 본다는 뜻이다.
- 위치를 값으로 복사해 넘기면 sdpa와 잡음 수준으로 같아진다. 원인이 참조로 전달된 위치라는 뜻이다.
- 새 캐시에서는 빈 칸의 키가 0이라 그 칸이 받는 가중치가 거의 없어서 차이가 드러나지 않는다. 캐시를 비우지 않고 재사용하거나 위치를 되돌려 다시 쓰면 이전 요청이나 이전 시도의 데이터가 답에 섞인다. E3에서 최상위 토큰이 바뀐 것이 그 경우다.
- 같은 코드가 2026-09-22 기준 transformers 메인 브랜치에도 있다. 빠른 검색으로는 같은 보고를 찾지 못했다.
- **보통 사용에서의 영향은 작다(후속 확인, `realworld/local_checks.md`).** `generate()`는 호출마다 0으로 찬 새 정적 캐시를 만든다. 실제 `generate()`로 탐욕 생성을 비교하자, 결함이 있는 경로와 고친 경로의 차이는 어텐션 구현을 바꿀 때 생기는 수치 잡음과 같은 크기였다. 이 결함은 캐시를 비우지 않고 재사용하거나 위치를 되돌려 쓰는 경우에만 답을 바꾼다. 실제 결함이지만 사용자가 흔히 겪는 문제의 증거로 쓰기는 어렵다. 같은 확인에서 내장 FlexAttention 경로는 긴 프롬프트에서 컴파일 오류로 멈췄다.

이 결함의 성격: "질의 위치는 p"라는 사실이 값이 아니라 "이 카운터를 읽는 순간의 값"이라는 참조로 전달됐다. 언제 읽느냐에 따라 뜻이 바뀌었고, 어느 계층도 이를 검사하지 않았다. 조사 체계로 보면 카운터는 마스크에게 "에서"(읽는 출처)이고 캐시 갱신에게 "에"(쓰는 대상)다. 읽는 쪽이 붙잡고 있는 동안 쓰는 쪽이 바꾸는 형태는 Rust의 빌림 검사가 거부하는 형태와 같다. 역할을 검사하는 컴파일러라면 이 충돌을 컴파일 단계에서 잡을 수 있다. rolec은 "까지"를 호출 시점의 값으로 묶으므로 이 경우가 생기지 않는다.

### 7.3 E6: 한 선언, 두 백엔드

`e6_one_spec.py`. 같은 rolec 호출을 손 커널과 FlexAttention 두 백엔드로 내렸다. Flex 백엔드는 "까지"에서 블록 정보를 산술로 계산한다. 기준값은 뜻을 풀어 쓴 fp32 계산(키 ≤ last[b], 헤드를 그룹마다 반복)이다. 행마다 last를 0, 127, 128, 300, 511, 639로 두어 블록 경계와 "포함" 규칙을 모두 건드렸다.

| 백엔드 | 기준값과 최대 차이 | 호출당 시간 |
|---|---|---|
| 손 커널 (Triton) | 0.0019 | 0.19 ms |
| 범용 컴파일러 (FlexAttention) | 0.0019 | 1.55 ms |

- 두 백엔드 모두 모든 행에서 bf16 반올림 수준으로 기준값과 같았다. last가 0인 행은 두 백엔드 모두 차이가 정확히 0이었다.
- 역할 검사는 백엔드와 무관하다. Flex 백엔드에서도 키와 값을 바꿔 넘기면 실행 전에 거부됐다.
- Flex의 호출당 시간은 블록 정보를 파이썬에서 매번 만드는 고정 비용이 대부분이다. 그래프 안에서는 이 계산이 12 µs다(E3). 속도 비교가 아니라 같은 뜻을 두 경로로 낼 수 있는지를 본 실험이다.

## 8. 판정

### 8.1 기존 컴파일러는 의미를 비효율적으로 찾는가: 대체로 아니다

- 컴파일 중 의미 복원은 콜드 컴파일의 약 20%이고 한 번만 낸다(E1).
- 매 호출 6,432개의 가정을 다시 검사해도 비용이 보이지 않는다(E1).
- 디코드에서 지워진 구조를 매 스텝 다시 찾는 비용은, 컴파일해 그래프 안에 두면 스텝의 1% 안팎이다(E3).
- 긴 문맥의 블록 구조 재발견은 32K까지 어텐션의 1~2%, 128K에서 약 5%다(E3b).
- 예외는 두 가지다. 재발견을 자연스러운 방식, 즉 호스트에서 매 스텝 부르면 스텝이 절반 이상 느려진다. 또 재발견은 N의 제곱으로 자라 매우 긴 문맥에서는 어텐션보다 커진다. 둘 다 전문가가 피하거나 아직 먼 규모의 문제다.
- 따라서 "기존 컴파일러가 비효율적으로 찾는다"는 가설은 손실의 주된 원인으로는 기각한다. 탐색은 싸고, 전문가가 쓰면 더 싸다.

단, 탐색은 싸지만 약하다. E3에서 재발견은 선언보다 약한 사실을 얻었다(다섯 블록 모두 "일부 유효"). E2에서 `mark_dynamic`의 힌트는 크기 1에서 무시됐다. 찾거나 힌트를 받는 방식으로 얻은 사실은 선언된 사실보다 약하거나 불확실하다.

### 8.2 의미가 추상적으로 전달되어 손실이 생기는가: 그렇다, 크게

- **성능:** 유효 범위와 헤드 공유라는 두 사실이 참/거짓 표와 복사로 풀려 전달되면 디코드 스텝이 1.3~2.5배 느려진다(E4). 이 차이는 탐색 비용이 아니다. 받은 쪽에는 이미 그 사실이 없다.
- **지연의 안정성:** 배치 크기를 관측으로 추측하면, 추측이 틀리는 순간 1~2분 멈춘다(E1, E2).
- **답의 안정성:** 역할이 모호하거나 사실이 엉뚱한 때에 읽히면 틀린 답이 경고 없이 나온다. 주입한 역할 실수 8종이 모두 무증상이었다(E5). 주입하지 않은 실제 결함도 있었다. transformers 내장 Flex 경로는 질의 위치를 참조로 넘겨 한 칸을 더 읽었다(7.2절). 여기에 3주차에 조용히 삼켜진 `cache_position`, E5에서 조용히 삼켜진 `sliding_window`, E2에서 조용히 무시된 `mark_dynamic`을 더하면, 넘긴 정보가 쓰이지 않거나 다른 때에 읽힌 사례가 이번 연구에서만 네 번 나왔다. 넷 모두 라이브러리의 실제 동작이다.

### 8.3 역할을 선언하면 해결되는가: 이번에 잰 범위에서는 그렇다

- 의미 소거: 사실을 받은 범용 컴파일러가 손 커널, 컴파일 시점 상한과 같은 속도를 냈다(E4). rolec은 같은 선언을 손 커널과 FlexAttention 두 경로로 내렸고 둘 다 기준값과 같았다(E6).
- 재발견: "까지"에서 블록 정보를 산술로 얻으면 12 µs이고 길이와 무관하다(E3, E3b).
- 추측: 배치를 값 모르는 크기로 선언하면 컴파일은 한 번, 크기 집합을 선언하면 서비스 중 멈춤은 0이다(E2).
- 조용한 오류: rolec은 8종을 모두 막았다(E5). 7.2절의 결함은 "까지"를 호출 시점의 값으로 묶는 규칙에서는 생기지 않는다.

## 9. 탐색이 문제가 아니라면, 조사 기반 컴파일러의 이점은 무엇인가

"더 빨리, 더 확실하게 찾는다"는 이점이 되기 어렵다. 기존 컴파일러의 탐색은 이미 싸다. 이점은 다음 다섯 가지로 다시 세운다. 앞의 둘이 핵심이다.

1. **전문가 경로가 기본값이 된다.** 지금 1.3~2.5배를 얻으려면 프로그래머가 FlexAttention과 `enable_gqa`를 알아야 하고, 블록 마스크를 그래프 안에 두는 법(E3)과 라이브러리 경로의 함정(7.2절)까지 알아야 한다. 조사 문법에서는 이 사실들이 문장의 필수 성분이라 빠질 수 없다. 그래서 기본 번역이 곧 전문가 경로다. 근거는 E4, E3, E6.
2. **조용한 오류가 문법에서 사라진다.** 현재 스택은 역할 실수를 하나도 잡지 못했다(E5). 라이브러리 안에서도 같은 종류의 결함이 나왔다(7.2절). 성능 도구와 테스트는 이런 오류를 찾기 어렵다. 판단에 필요한 정보, 즉 "이 인자의 역할이 무엇인가"가 프로그램 안에 없기 때문이다.
3. **추측 없는 컴파일.** 배치가 바뀔 때 1~2분 멈추는 문제가 선언으로 사라진다(E2). 무엇을 몇 번 컴파일할지 서비스 전에 안다.
4. **찾을 수 없는 것을 선언한다.** 배치와 무관하게 같은 답(3주차, 비트 단위 동일, 비용 0~3%)은 프로그램의 사실이 아니라 프로그래머의 요구다. 아무리 잘 찾는 컴파일러도 요구를 찾아낼 수는 없다. "마다" 같은 조사로만 전달된다.
5. **한 명세, 여러 백엔드, 검증 기준.** 같은 선언에서 손 커널 경로와 범용 컴파일러 경로를 만들고, 뜻을 풀어 쓴 기준값으로 둘 다 검사했다(E6). 새 하드웨어용 커널이나 AI가 생성한 커널을 검사하는 기준으로도 쓸 수 있다.

업계가 같은 방향으로 가고 있다는 증거도 이번 실험에 있다. PyTorch는 FlexAttention의 마스크 함수, `enable_gqa`, `mark_unbacked`의 `shape_id`(여러 텐서가 같은 배치라는 관계의 선언)를 하나씩 따로 추가했다. 모두 선택 사항이고, 흩어져 있고, 그중 일부는 조용히 무시된다. 조사 기반 컴파일러의 차별점은 이것들을 하나의 필수 문법으로 묶고 검사하는 데 있다.

한 문장으로: 이 컴파일러의 이점은 "의미를 빨리 찾는 것"이 아니라 "의미가 지워지지 않고, 잘못 전달될 수 없는 것"이다.

> **2026-09-22 개정.** 이 절의 "조사 문법"은 필수 선언 일반으로 읽는다. 연구자의 언어 '글'을 확인한 뒤, 값의 성질("마다"가 뜻하는 배치 불변성, "까지"가 뜻하는 유효 범위)은 조사가 아니라 타입이 담는 것으로 고쳤다. 조사가 담는 것은 방향, 변환 대상, 동반뿐이다. `RESEARCH_PLAN.md` 5.3절과 `ideas/josa_role_semantics.md` 9절을 본다.

## 10. 한계와 다음 단계

한계:
- rolec은 파이썬 시제품이고 검사를 호출 시점에 한다. 사용자 언어에서는 컴파일 단계 검사가 되어야 한다.
- 측정은 한 모델(Qwen3-4B), 한 GPU(4070 Ti), 디코드 중심이다.
- E5의 역할 실수 8종은 제가 고른 것이다. 실제로 얼마나 자주 일어나는지는 재지 않았다.
- E1에서 Dynamo와 AOT 시간을 "의미 복원"으로 본 것은 해석이다. 두 단계에도 의미와 무관한 일이 섞여 있다.
- 7.2절의 결함은 이번 하네스처럼 캐시에 이전 데이터가 남는 조건에서 드러났다. 실제 서비스에서 얼마나 자주 그런 조건이 생기는지는 확인하지 않았다. 상위 저장소에 보고하지 않았다.

다음 단계 제안:
1. 사용자 언어의 실제 조사 규칙을 받아, 어텐션 명세 하나를 그 언어로 쓰고, 역할을 보존하는 중간 표현에서 Triton과 FlexAttention 코드를 생성하는 최소 경로를 만든다.
2. 변형을 늘린다. 슬라이딩 윈도("부터…까지"), 문서 묶음 마스크, MoE 라우팅("마다", "만")에서 같은 측정을 반복한다.
3. transformers, vLLM 같은 저장소의 버그 기록에서 역할 종류의 결함을 표본 조사해 빈도를 잰다. 이점 2의 크기를 실제 데이터로 뒷받침하는 핵심 근거가 된다.
4. 7.2절 결함의 상위 보고 여부를 정한다.
